VM-backed isolation for rv: apple/container and tart

How rv can add a VM boundary around contained agent launches on macOS: Linux micro-VMs through Apple's Containerization library, macOS guests through tart, and what each closes in the Seatbelt cage's open P0 list.

01Why this matters now

rv is a fail-closed policy gate for coding agents. On macOS the contained launch is a Seatbelt cage: sandbox-exec with a deny-default SBPL profile, a private hdiutil volume, and loopback-only network to rv's secret gateway and egress proxy. Four P0s in docs/security/runtime-mechanism-decision.md remain blocked because native mechanisms cannot close them.

P0Problem todayWhat a VM boundary does
ISO-01 sysctlCage can read host kernel stateGuest kernel is not the host kernel
ISO-02 guardianNo reliable supervisor for the whole cageThe VM is the guardian: stop it and everything dies
ISO-03 Linux LandlockNo contained launch on Linux hosts (containedGuaranteesUnsupported)Unchanged for Linux hosts. rv's Linux build gains a place to run on Macs: inside the guest
ISO-04 descendant execEndpoint Security vs brokered exec, unresolvedEvery descendant is inside the VM; exec is mediated by vminitd and by rv's own Linux hooks in the guest

runtime-remediation-plan.md:63 already anticipates this: "an entitled service or VM backend requires a bounded reviewed extension if native mechanisms cannot pass." Line 62 adds: "Container-provided isolation is not RV evidence."

The plan respects both. The VM backend is a new, separately evidenced backend family with its own acceptance criteria, not a shortcut around the existing ones.

Competitive context: Infisical and Varlock now ship Seatbelt + placeholder + proxy. OpenShell drives Docker, Podman, K8s and VMs and talks about the "container tax on Mac". VM-grade isolation on a Mac with no Docker Desktop and sub-second start is a position none of them hold.

02What the two projects give us

apple/container + Containerization

Linux guests · Apache-2.0 · CLI 1.6.1 (2026-10-23) · library 0.54.0 (2026-10-28)
  • One lightweight Linux VM per container on Virtualization.framework. OCI images. Sub-second boot.
  • The library runs without the container daemon. Apple's own examples/sandboxy boots a micro-VM per agent session (Claude Code, Pi) with a virtio-fs workspace, host-only network and an allowlist CONNECT proxy. That is rv's shape minus policy, secrets and audit.
  • Embed API: ContainerManager → LinuxContainer with mounts (virtiofs share, ext4 block, tmpfs), cpus, memory, dns, masked and read-only paths, unix-socket relays, dialVsock, exec, copyIn/copyOut. Read-only rootfs plus overlay via writableLayerSizeInBytes.
  • Needs a Kata kernel file, the vminit image pinned to the library version, and the com.apple.security.virtualization entitlement on the driving process.
  • Gates: vmnet is macOS 26 only; still 0.x with breaking minors; Rosetta for amd64; partial memory ballooning. Osaurus ships the dual mode rv would need (Containerization on 26, sandbox-exec below).

tart

macOS + Linux guests · FSL-1.1 → Apache-2.0 after 2 years · 2.41.1 (2026-10-15)
  • Swift CLI over Virtualization.framework; VM images as OCI artifacts; clone is an APFS copy-on-write clone; run --no-graphics --dir=ws:path[:ro] --net-host|--net-softnet --root-disk-opts=ro; tart exec over a vsock guest agent on Cirrus images, otherwise tart ip + ssh.
  • Ownership changed. Cirrus Labs joined OpenAI on 2026-04-07; the repo is now openai/tart. License moved to FSL-1.1 on 2026-06-05: internal and non-competing commercial use are fine; a product that substitutes for tart is not. The licensor ships Codex.
  • The fork christopherkarani/tart is an unmodified snapshot: 0 ahead, 44 behind, HEAD at upstream 2026-08-18.
  • CLI only, no library product. Shell out, or vendor sources.
  • Hard limits: Apple caps two concurrent macOS guests per host. Images are 25–73 GB. Boot to usable ~30 s macOS, ~8 s Linux. Headless use on macOS 15+ needs an unlocked login keychain.

03Architecture: two new backend families

The seam exists already in Sources/RVIsolation/IsolationApply.swift. The change is additive on the enums; IsolationGuarantees stays the contract, and a VM backend must establish every field or refuse the launch, exactly as RVDomain/Isolation.swift says today.

// today
IsolationBackendFamily { none, seatbelt, landlock }
Launch { seatbelt(SeatbeltProfile), landlock(LandlockRuleset), unsandboxed }
EstablishedIsolation { observed, mediated, seatbelt(RuntimeSession) }

// proposed
IsolationBackendFamily { none, seatbelt, landlock, microvm, macvm }
Launch { ..., microvm(MicroVMPlan), macvm(MacVMPlan) }
EstablishedIsolation { ..., microvm(RuntimeSession), macvm(RuntimeSession) }

Process layout for the micro-VM backend

Mapping today's mechanisms

Seatbelt todayMicro-VM
Private hdiutil volume, copy-back on close (WorkspaceInodeBoundary.swift)Sparse ext4 block mount built from the workspace; copyOut on close. Virtiofs share stays available as the fast-iteration option for read-mostly trees
Deny-default SBPL profileRead-only rootfs plus overlay, masked and read-only paths, reduced caps, no network interface at all unless the plan says mediated
Loopback-only TCP to gateway and egress on the hostHost loopback is unreachable from a guest. Expose gateway and egress as unix-socket relays or vsock ports; a small guest-side forwarder binds them to 127.0.0.1 inside the guest so HTTPS_PROXY and the rvph_ base URLs keep working unchanged
Process group + SIGKILLLinuxContainer.stop(); the VM is the guardian (ISO-02)
Admission broker on fd3/4/5Same protocol over a vsock port
ContainedEnvironmentPolicy denylistUnchanged; applied to the guest process environment

A known gap closes as a side effect: "any loopback process can spend a placeholder" stops being true for VM launches. Only processes inside the guest can reach the relay.

Process layout for macOS guests (tart)

rv-vm-host ── spawn ── tart clone <golden> rv-<session>
                       tart run --no-graphics --dir=ws:<path> --net-host --root-disk-opts=ro [--net-softnet on 26]
                       tart exec rv-<session> -- rv-guest-launch …   (guest-agent images) | ssh fallback
                       tart stop / delete on close

Inside the macOS guest, rv runs with the existing Seatbelt cage: VM boundary outside, Seatbelt inside. Admission control counts live macOS guests and refuses the third.

04Phases

Phase 01 week
throwaway

Spike and gates

  1. Daemon-less PoC modelled on examples/sandboxy: boot a micro-VM with an rv workspace, run Claude Code inside, egress through rv's proxy over a vsock relay. Measure cold and warm boot, virtiofs vs block I/O on a node_modules-heavy repo, idle RSS.
  2. Prove com.apple.security.virtualization on a Developer ID signed, notarized, non-bundle Mach-O helper through release.yml. If it must be a .app, know now.
  3. Legal read of FSL-1.1 for the tart shell-out. Go/no-go on macOS guests, independent of the Linux work.
  4. Decide the macOS 26+ floor for VM backends (Seatbelt stays on 15). Recommendation: yes, mirror Osaurus.
Exit: numbers in a short memo and a go/no-go per backend.
Phase 13–4 weeks

Seam first, then the micro-VM backend

  1. Close the seam bypass. WorkspaceSessionSupervisor.swift (~664, ~1215) calls prepareSeatbelt directly and runSeatbeltLaunch is Seatbelt-specific. Route the interactive path through IsolationBackend.prepare/run. No behavior change; covered by existing L2 tests.
  2. Add microvm to the family, launch and established enums. Add MicroVMPlan (kernel, init image digest, cpus, memory, mounts, relays).
  3. New target rv-vm-host, entitled, linking Containerization at an exact: version. Nothing else in rv links it.
  4. Provisioning in rv setup and rv doctor: kernel download with digest pin, vminit image pinned to the library version, macOS version and Apple Silicon gates.
  5. Workspace as an ext4 block image with copyOut on close; close/abandon/leftovers semantics preserved.
  6. Release assets and installer updated.
Exit: rv workspace start --isolation contained --backend microvm runs an agent end to end with network .denied.
Phase 22–3 weeks

Secrets, egress and evidence

  1. Vsock and unix relays for the secret gateway, egress proxy and admission broker. Guest-side forwarder shipped in a rootfs image built with container build.
  2. Run rv's Linux build inside the guest: hooks for the agent, rvd, Landlock around the agent process. ISO-03's Linux work gets a shipping surface; ISO-04 gets a second layer.
  3. Write the ISO-05 microvm section in runtime-acceptance.md and runtime-boundary.md, including the sandboxy caveat: the guest must not reach host services bound on 0.0.0.0; rv binds relays only.
  4. L2 tests on the macos-26 CI shard; adversarial script variant that runs inside the guest.
Exit: the four P0s have a documented status under the micro-VM backend; remediation plan updated.
Phase 33 weeks
only if Phase 0 says go

macOS guests via tart

  1. macvm family and MacVMPlan. Shell out to a pinned tart release detected by tart --version; no source vendoring. Keep the fork as a snapshot and re-sync it to a tagged release.
  2. rv vm image pull/list/prune for golden images (OCI, Packer-built); clone per session, delete on close.
  3. Networking: --net-host plus rv egress on the host; --net-softnet on 26 when the helper is installed.
  4. Launch via tart exec on guest-agent images; ssh fallback with a per-session key.
  5. Admission: enforce the two-guest cap with a clear error.
  6. rv runs inside the guest with Seatbelt, baked into the golden image.
Exit: rv workspace start --backend macvm runs xcodebuild in a contained macOS guest.
Phase 41 week
parallel to Phase 1

Developer velocity

  1. Scripts/isolation-linux-adversarial.py: add a container driver next to Docker so Mac developers run the Linux Landlock suite without Docker Desktop.
  2. container build recipe for the Linux release artifacts to reproduce release.yml locally.

06Decisions needed

macOS 26+ floor for VM backends, Seatbelt stays on 15?
Recommended: yes.
Pursue macOS guests via tart at all, given FSL-1.1 and OpenAI as licensor?
Recommended: spike only; decide after legal.
Fork strategy for christopherkarani/tart: snapshot only, or vendor sources?
Recommended: snapshot only, re-synced to a tagged release.
Order: micro-VM first, or tart first because Xcode workflows matter more to current users?
Recommended: micro-VM first.

07Non-goals

  • Replacing Seatbelt. It remains the macOS 15 path and the inner layer inside macOS guests.
  • Linux-host contained launch (ISO-03 on Linux hosts) is unchanged by this plan.
  • Running rv's CoreML judge inside guests.
  • Kubernetes or container cluster.
