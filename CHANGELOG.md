# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- New CLI commands and flags from a hands-on usability pass: `rv status` (one-screen health: service, guard mode, hosts, ledger; exit 1 when unhealthy) and `rv version` (also `-V`); `rv setup --dry-run` lists which hook and service files setup would write, refresh, replace or skip, and writes nothing; `rv audit forward --status` shows the target, cursor position, pending events and schedule without sending. A mistyped subcommand now suggests the closest one (`rv stauts` → `rv status`, exit 64).
- macOS: the Laya judge runs in a supervised worker pool, `dev.rv.judge` (`rv-judge serve`), instead of inside rvd. Two worker processes hold the model: the primary on the CPU only, the hedge on the GPU (production compute units); measured under load, the CPU worker's p95 is 19–34 ms against the GPU's 335 ms. A request goes to the primary; one that finds the primary busy waits up to 40 ms for it before going to the hedge, and if the primary has not answered after 150 ms the request also goes to the hedge, and the first answer wins. A worker still busy at the 1.5 s budget is killed (SIGKILL is the only way to stop a Core ML prediction) and restarted; a crashed worker is restarted with backoff, and three faults in five minutes take a worker out of rotation for ten (all calls then go to the other one); a model change keeps that history and is refused within 10 s of the last one. At most 8 requests wait; more are refused at once. Each call is answered within its budget, so a Core ML abort, LLVM out-of-space crash or hung prediction costs one judged call a review prompt, not rvd. Workers load the compiled model only through the verified store under `~/.config/rv/cache/laya` (shared with rvd and the CLI, locked so two workers warming at once compile once, and never sweeping an entry another worker has loaded), each with its own Core ML crash marker: one worker's crashes move only that worker to CPU, and a worker the supervisor kills for running over its budget is not counted as a crash. A load the worker refuses goes to review (`judge-refused`). The workers' Core ML cache, `~/Library/Caches/rv-judge`, is guarded like rvd's: agent writes there (file tools and shell) deny in enforce and observe mode, MCP cages cannot write it, and workspace downloads cannot land there. The MCP cage's profile cap rises from 288 KiB to 304 KiB so a letter-heavy home still fits with that extra deny. `rv doctor` names a `~/.config/rv` or judge cache directory another account can write. They pay the slow first prediction before they report ready. `rv setup` registers the agent before rvd when `rv-judge` is installed beside it and warns, with a judge bundle installed, when it cannot; like rvd's, the agent is `RunAtLoad` with `KeepAlive` while `rv-judge` exists, and `rv doctor` warns when its plist is not, or when it is loaded in both launchd domains; the installer now installs `rv-judge`, and `rv uninstall` removes the agent. rvd's doctor snapshot gains a `judgePool` check (workers, compute units, restarts, routing), and `rv doctor`'s human output now lists rvd's judge warnings and, on macOS, a missing or unloaded judge agent. Design: `docs/architecture/judge-pool.md`.
- rv Console (`dashboard/`): a self-hosted fleet dashboard that receives `rv audit forward` batches (OCSF or `--format rv`, deduplicated by uid) and `rv report --json` posture, behind bearer ingest tokens. Pages: overview, a searchable activity log with export, detections by rule and pack, fleet compliance, MCP gateway, secrets, policy changes (loosening without owner authentication is flagged) and integrity, which checks each machine's audit hash chain off the machine. It also has OpenID Connect single sign-on (Okta, Entra ID, Google Workspace and others) with domain and group-to-role policy and optional enforcement, and Slack and HMAC-signed webhook alerts for chain breaks, secret misuse, forged MCP approvals, unauthorized loosening, non-compliant devices, block spikes and silent devices. Ships a Dockerfile and a demo mode with a synthetic fleet.
- `rv policy status [--json]` reports whether rvd loads the current machine and repo policy, which revisions, and why not. rvd answers from the load hooks run. A policy rvd cannot load denies every action (`typed-rules-invalid`); rv never falls back to an earlier policy. `rv policy draft|apply|rollback --save --wait [--wait-timeout s]` blocks until rvd loads the saved policy. Exit 1 when rvd reports a failed load. Exit 3 whenever rvd did not answer (unreachable or busy): the report is then the CLI's own view, loaded or failed, and nothing confirms rvd enforces it. A policy file that is a FIFO, device or other non-regular file, or larger than 1 MiB (256 KiB for the ceiling), now fails closed with a specific reason instead of being waited on or read whole; a symlinked `policy.toml` still loads when its target is a regular file (the ceiling never follows symlinks). Saves that would exceed 1 MiB are refused.
- `rv workspace upload <host-path> [<workspace-path>]` and `rv workspace download <workspace-path> <new-host-path>` move files in and out of a live workspace mid-session, for Seatbelt and both VM guests (all of them work on the workspace volume). Both ask for owner authentication first and are refused when an agent issues them. Selection honours the copied tree's `.gitignore` files (`--no-gitignore` turns that off); `.git` directories are never copied. A transfer never reads, writes or copies through a symlink, refuses FIFOs, sockets, devices, unsafe names, and trees over 20,000 entries, 2 GiB or 64 levels; uploads refuse rv's config dir, hard-linked files and rv/git control and run-later paths in the workspace; downloads only create a new destination outside the workspace and rv's config and install dirs, refuse to put a run-later or control file (`.envrc`, `.claude/settings.json`, ...) at the top of it, drop set-id bits, and remove a partial copy on failure. The host parent is pinned by descriptor and must still be the one the owner approved. Known false refusal: the agent-issued self-protection check also holds `rv workspace --workspace "$PWD" status`, because it cannot tell the value of `--workspace` from a subcommand.
- `rv doctor` checks every role in an installed peer-trust manifest whose binary rv installed, not only `service`: `cli` (`rv-cli`), `workspaceHost` (`rv-workspace-host`) and `mcpCustodian` (`RVApprovals.app`). A binary its entry does not match is a `warn` row such as `peer-trust-role-unsatisfied-workspaceHost` ("the peer-trust manifest pins the workspace host to a different build; rv workspace and rv opencode will not start"), naming both builds, with a fix that points at `/Library/Application Support/RV/peer-trust.json` and says updating it needs an administrator. A build pinned by cdhash now also reports its Developer ID signer when it has one. With `rv-workspace-host` installed, doctor also warns (`peer-trust-workspace-roles-missing`) when no manifest is installed or the manifest has no `workspaceHost` or `cli` entry, since only the manifest grants those roles. `rv doctor --json` only gains `problems` rows.
- The OCSF audit export (`rv audit export --format ocsf`, `rv audit forward`) carries a stable reason code in `status_code` on every denial and would-be denial (for example `rv.egress.denied-policy`, `rv.secret.foreign-placeholder`, `rv.command.denied-secret-path`), and declares its OCSF profiles in `metadata.profiles`. Every audit kind is now validated in CI against vendored OCSF 1.3.0 schemas; API and Process Activity events always name an `actor`, Process Activity a `process.uid`, and Application Lifecycle's `app` a `vendor_name`, as 1.3.0 requires. API and Process Activity events rv cannot attribute to an agent (such as TTY and human commands and MCP gateway calls) used to have no `actor` and now carry `actor.app_name: "unknown"`; rules that test for a missing `actor` need to test for that value instead. `process.uid` is the event's own uid, not a process identity: it does not correlate events of the same process. The MCP gateway's own refusals are coded apart from a policy deny (`rv.mcp.inexact-number`, `rv.mcp.unserved-tool-name`, `rv.mcp.hiding-schema`, `rv.mcp.hiding-untracked`, `rv.mcp.not-listed-since-restart`), though their records say policy `deny`. The codes are listed in `docs/guides/audit-log.md`.

- `rv blocks` rows, `rv blocks --json` and the `command.denied` / `command.observed` audit detail name the agent session that tripped the rule (`session`; `session=<id>` at the end of a text row), taken from the host's hook payload (`session_id`). Only opaque ids (letters, digits, `.`, `_`, `:`, `-`, at most 128 bytes) are kept; rows from the TTY, from hosts that send no session, and rows written before this release carry none. The OCSF export maps it to `actor.session.uid`.
- rvd writes one line to `rvd.log` when a hook evaluation runs past its deadline (the case the agent sees as "RV daemon did not answer in time"): host, door, rule or reason id, and milliseconds per phase (queue, offload wait, inputs, policy, screen, judge load, judge admission, judge prediction, gate, effects, reply). A request still running 10 seconds past its deadline is logged once with the phases measured so far ("still running"). No command text, path or session id; at most one line a minute, the next written line counting the skipped ones. "Still running" lines have their own one-a-minute window, so a stream of late completions never hides a stuck request.
- With `guard.mode` observe, the rvd `evaluate` RPC (the SDK's `evaluate`) also returns the verdict enforce would have returned, in a new optional `wouldBe` field beside the observed allow in `result`, the same verdict `rv test` shows. It is present only when observe changed the outcome, so it is absent in enforce mode and for a command enforce would also allow. The Python SDK exposes it as `Evaluation.would_be`. Older clients ignore the field. The explain and classify RPCs still report the observed verdict.

- For rv's own tests: a debug build made with `RV_TEST_OWNER_PRESENCE=1` (never a release build) lets rvd check owner approvals on Linux against a password in its environment, so allow-once and owner actions run end to end with nobody present (`Scripts/test-owner-presence-e2e.sh`). Release staging fails if a binary carries it (`Scripts/check-no-test-owner-presence.sh`). See `docs/security/test-owner-presence.md`.

### Changed

- CLI usability pass (one bundle):
  - An agent's refused `rv` command says rv blocks agents from weakening it, instead of "could not finish evaluating"; a matcher timeout on a long command says rv ran out of time. Agents may run `rv <verb> --help`, `rv <verb> <sub> --help` and `rvd --version`.
  - `rv blocks` is a table (time, decision, host, tool, rule, target) with a per-rule summary, `--limit` (default 20), `--all`, `--rule` and `--host`; observe rows read WOULD BLOCK / WOULD ASK.
  - `rv service` exits 1 when rvd is not running, and `rv doctor --json` lists the service state in `problems`. Doctor shows the guard mode, labels the API version, and leads Next with the service fix.
  - `rv explain` exits 1 on a deny, like `rv test`; its JSON has no reason on allow. Help pages gain Exit codes sections.
  - `rvd --help` prints usage instead of starting a second daemon; an unknown rvd argument exits 64.
  - Owner-only commands say why they need a terminal; `rv allow-once` help explains codes. Ask denials give one approval instruction. The out-of-repo and unwrap-limited denial reasons are reworded.
  - Bare `rv` without a terminal prints the command list. `rv host` and `rv host mode` with no arguments list the current modes. `rv packs` shows what is on unless `--all`, `--verbose`, `--category` or `--search` is given. `--no-color` keeps human output when piped.
  - `rv audit --kind` refuses a kind that matches nothing and lists the families; an empty tail says why.
  - A long usage line no longer pads every help row. `rv init` help says it is optional and is not setup; secrets help, the egress footer and the README observe paragraph are plainer.
- On macOS rvd no longer loads Core ML. Every judged call goes to `dev.rv.judge`; when the pool does not answer in time, is not running, or cannot be verified, the call goes to review (`judge-late`, `judge-unreachable` in the judge log), never to an unjudged allow. An installed bundle that fails to load in a worker now goes to review too; before, a load failure ran packs-only. Upgrading without re-running `rv setup` leaves the agent unregistered, so judged calls ask until `rv setup` runs. The supervisor and rvd authenticate each other like rvd and its hooks: an installed peer-trust manifest must list a `judge` entry for the supervisor, or rvd treats the pool as unreachable. `rv test` and the bench CLI still run the judge in-process. Linux is unchanged (packs only).
- rvd is always on on macOS. The LaunchAgent is now `RunAtLoad`, with `KeepAlive` while the rvd binary exists (relaunch throttled to once every 5 s), so launchd starts rvd at login and restarts it right after a crash, instead of waiting for the next hook call to cold-start it (model reload, `judge-warming`, then review or ask). Deleting rvd stops the relaunches. KeepAlive used to be on only when the companion app was installed; that probe is gone. rvd no longer idle-exits by default (it did after 30 minutes when launchd started it on demand); `--idle-exit-seconds N` still opts in. Linux setup already kept rvd running (systemd `Restart=always`, idle exit set to a year), and so does rv starting rvd itself when no systemd user manager runs, though nothing restarts that one after a crash. rvd still exits once its binary is replaced, and launchd or systemd then run the upgraded one; `install.sh` now replaces rvd last, after the packs, runtime libraries and helpers it loads. A crash-looping rvd started by launchd or systemd backs off: once two runs in a row die within 30 s of starting, each further start binds its socket, then waits before it accepts anything (5 s, doubling up to 5 minutes), and skips warming the judge (the judge then loads on the first judged request, so a Core ML abort can still happen there). While it waits, hooks see a slow rvd and ask or deny; observe mode does not step aside. A run that lasts 30 s, `rv setup`, or an `rv service restart` or `rv service start` that starts rvd clears it. rvd run by hand, by the SDK or by rv itself never waits. The record lives in `rvd-backoff/` beside rvd's log, which agents may not write (a planted record would hold rvd in its wait). So deleting, moving or changing the mode of `~/Library/Logs/rv` or `~/.local/state/rv` (or their parents) is now denied too, as for other rv wiring; rvd's log itself stays writable. On Linux, connections that queued on rvd's socket during the wait are closed, not served late. On macOS, hooks reach rvd over XPC, and launchd still delivers messages it queued during the wait once rvd starts, so a hook that already gave up (and asked or denied) can have its request evaluated late. A configuration error that cannot fix itself (no usable home, bad socket path) waits 60 s before exiting when launchd or systemd started rvd. rvd's log is now rotated at 1 MiB while it runs, not only at start. The judge model stays loaded for as long as rvd runs. `rv uninstall` boots the job out before it removes the plist and rvd, so nothing respawns. `rv doctor` reports `KeepAlive true idle-exit off`, warns when the installed plist is an older on-demand one or the job is loaded in both `gui/` and `user/` (and says to run `rv setup`), and when rvd is in its startup backoff. `rv service restart` and `rv service start` on macOS now wait for rvd to answer, as `rv setup` and Linux already did, and fail (exit 69) when it does not; from an SSH session, which cannot reach a `gui/` job's Mach service, they check with `launchctl print` that rvd runs and stays up, and fail (exit 69) when the job is not found or launchd shows no state. A home path with `&`, `<` or `>` no longer breaks the LaunchAgent plist. The Python SDK's `ensure_runtime` now spawns rvd with a 30 minute idle exit by default, since nothing supervises it (`idle_exit_seconds=None` keeps it up).
- A deny no longer rewrites the whole denial ledger: `blocks.jsonl` gets one appended line, and is rewritten down to 200 rows and 7 days only once it holds 50 rows more, a row past 7 days, or rows another process wrote. `rv blocks` still shows at most 200 rows, and `rv audit forward`'s `blocks.jsonl` cursor restarts about once per 50 denies instead of on every deny. rvd also writes its analytics counters at most once a second instead of after every decision, and not at all when the enabled packs are unchanged; an idle or replaced-binary exit writes what is pending, while a crash or SIGTERM can lose up to a second of counts. Under load a deny now costs about what an allow does (8 concurrent denies: p50 47.5 ms to 7.8 ms on Linux).
- The `rv hook` front door can decide a call without rvd. It first runs `rv-hook-local`, a new executable next to `rv`, which runs rvd's own hook door over the same packs, policy and config and answers only when rvd could give no other answer: an allow that needs neither the judge nor the Policy gate, a deny no grant or human can lift, a file-tool verdict, or another tool's call. Everything else (the judge, a deny the Policy gate or a human may lift, observe would-be denies, anything unexpected) goes to rvd exactly as before. A locally decided call writes the judge-log, audit and denial-ledger rows rvd would have written; analytics events for it are not recorded yet. `rv-hook-local` is not in release builds yet, so until it is installed every call still goes to rvd. See `docs/architecture/hook-local-decide.md`.
- `rv setup` wires the Claude, Codex, Cursor and Antigravity hooks to a system `python3` this user cannot replace, instead of the first `python3` on `PATH`. Setup asks each candidate (with the hook's `-I -S` flags) for its real `sys.executable`, `sys.prefix` and standard library, and takes it only when root owns each of the three, every symlink on the way to them and every directory up to `/`, and this user can write none of them (a read-only directory this user owns does not count: its owner can make it writable again). On macOS it tries the Command Line Tools' `/Library/Developer/CommandLineTools/usr/bin/python3` first, then `/usr/bin/python3` only when `xcode-select -p` succeeds (so setup never opens the "install developer tools" dialog); `/usr/bin/python3` is an xcrun launcher, so setup bakes the interpreter it runs, never the launcher itself, which also saves each hook the xcrun hop. Xcode.app's Python is normally user-owned and does not qualify. On Linux it tries `/usr/bin/python3`. A miniconda, pyenv or Homebrew interpreter is one an agent could swap to skip the guard: setup falls back to `PATH` order only when no system candidate qualifies, and doctor's `adapter-runtime-replaceable-*` warning, which now applies the same resolved-path check to whatever is baked, says to install the Command Line Tools (`xcode-select --install`) and rerun `rv setup` on macOS (only to rerun `rv setup` when they are already installed), or to install `python3` with the package manager on Linux. Rerun `rv setup` to move an existing install.
- On macOS, `rv setup` writes adapter hooks as `/usr/bin/env <python3> -I -S <adapter>`. The Command Line Tools' Python is not a SIP-protected binary, so `DYLD_*` variables in an agent's environment reached it and could load code into the guard; `/usr/bin/env` is protected, and the dynamic loader drops them before the interpreter starts. `rv doctor` warns (`adapter-runtime-dyld-*`) about a hook that starts a non-system interpreter without `/usr/bin/env` and says to rerun `rv setup`, which rewrites 0.2.2's hooks without `--force`. `env` reads any word with `=` as a variable assignment, so on macOS setup skips a `python3` whose path contains `=`.
- Codex hook payloads without a `session_id` no longer use the `turn_id` as the session, nor Muse payloads the `turn_id`, nor Hermes payloads the `taskId`: a turn or task is not a session, so no block or audit row names one. It still keys the pending approval of an ask, so a human can approve it. An ask with neither a session nor a turn or task id creates no pending row, and the agent is told the ask was not recorded instead of being told to wait for an approval; the same holds when rvd has no pending-approval store.
- `rv egress pending`, `rv egress show` and the `rv tui` review pane name an approved proposal of the same workspace for the same host, any port, beside a pending one (`related approved api.example.com:443 (<id>)`; `related` in `--json`). The pending row stays listed and still needs its own decision. No row is retired or approved by another's approval.

### Security

- The admission HTTPS GET now refuses every address the egress proxy refuses. It treated the Azure WireServer address (168.63.129.16), the 6to4 relay anycast (192.88.99.0/24), the 3fff::/20 documentation block and most of 2001::/23 as public; the proxy, the admission GET and `allowed_ips` now read one address table. The admission GET still also refuses the IPv6 forms that embed an IPv4 address (such as NAT64 and 6to4), which the proxy judges by the embedded IPv4 address.
- `rv-hook-local` is checked before it reads the call, as `rvd` is: it must be the sibling next to `rv`'s own executable; on macOS it starts suspended and must carry the on-disk sibling's cdhash (no `peer-trust.json`) or be Developer ID signed `dev.rv.rv-hook-local` from the team the manifest pins rvd to (a development, cdhash-pinned manifest gets no local door); on Linux `/proc/<pid>/exe` must be the sibling. It runs with only `HOME`, `USER` and `LOGNAME` from the passwd entry and a system `PATH`, in `/`, for at most 1 s, and its reply must carry the request id and a compatible version. A missing, untrusted, slow, crashed or malformed evaluator sends the call to rvd; it never selects `RV_HOOK_WHEN_DOWN` or the observe step-aside. `judge-log.jsonl` appends are now flocked `O_APPEND` writes, safe across processes; the first row no longer replaces a file another writer created, and a writer holding the lock delays another by at most 200 ms in total (the row is then dropped, never the verdict; a drop in rvd is logged to `rvd.log`, a drop in `rv-hook-local` is not reported yet); writers of different JSONL logs in one process no longer wait for each other. Under observe, the local enforce cross-check uses the guard mode the evaluation itself read, so a `config.json` flipped mid-call cannot skip it. A code-signature check that outlasts the 1 s budget kills the evaluator before it runs.
- In Claude Code, a call rv could not check at all (rvd unreachable, slow or dropped, or the rv process past the adapter's 15 s budget) now gets Claude Code's own permission prompt instead of a hard block. The prompt shows the command or file path first, on one line with line breaks, backslashes and invisible or direction-changing characters escaped. It asks only when that whole escaped command or path fits in 300 characters; a longer one is blocked with rv's reason and a note that it was too long to show for approval, since any cut could hide part of it. Then "rv could not check this call (<layer>). An agent can cause this by stopping or overloading rvd. Approve only if you expected it." and rv's reason. It asks only when `RV_HOOK_WHEN_DOWN` is not `deny`, the permission mode is Manual (`default`), `plan`, `acceptEdits` or `auto`, Claude Code reports the session as attended (`CLAUDE_CODE_SESSION_ATTENDED=1`), and the owner has not pinned the block in `~/.config/rv/config.json` (read from the passwd home). The switch only tightens: only a missing file, or a JSON object whose top-level `hookAskWhenDown` is absent or exactly `true`, keeps the ask. Any other value (`false`, `"false"`, `0`, `null`, ...), a file that exists but cannot be used (a symlink, an unreadable or oversized file, corrupt JSON, `NaN` or `Infinity`), or a failed passwd lookup blocks. The switch is Claude-adapter-only: it does not close observe mode's step-aside for an unreachable rvd, which only `RV_HOOK_WHEN_DOWN=deny` does. `bypassPermissions`, `dontAsk`, a missing or unknown mode and an ordinary `claude -p` run still block. The attended check is a heuristic, not a boundary against anything that can start Claude Code: an agent can start `claude -p` so that it reports an attended session. An owner who wants no prompt sets `"hookAskWhenDown": false`. Only rv's three exact daemon-down messages, written with exit 0 and no top-level `decision`, count; any other native ask, rv's own review (approved in RVOperatorUI), a missing or unstartable rv binary, unusable output and identity or protocol failures still block. Whatever Claude Code routes prompts to answers this one, which can be an SDK callback, a `--permission-prompt-tool`, a `PermissionRequest` hook, a mod, or anything that can type into the terminal (`tmux send-keys`, `osascript`). "Yes, don't ask again" writes a persistent Claude Code allow rule; rv's deny still wins once rvd answers. If the adapter cannot write its answer it exits 2, which Claude Code treats as a block. Cursor and every other host still block. A deny that arrives without a reason now says "rv blocked this action without giving a reason. Run `rv doctor`." instead of "rv failed".
- Observe mode no longer lets tool calls through unchecked after `rvd` was stopped or crashed. Stopping `rvd` (`launchctl bootout`, `systemctl --user stop`, killing it, deleting its socket, or crashing it) used to turn observe-mode hooks into allow-everything. rvd now keeps a state marker, `~/.config/rv/rvd-state`: once it has run, a hook that cannot reach it asks or denies as in enforce mode ("rvd was stopped or crashed after it last ran ... Run `rv service restart`"), honouring `RV_HOOK_WHEN_DOWN`. A fresh install (rvd never ran) and an announced restart (`rv setup`, `rv service restart`, rvd exiting for an upgraded binary; a 60 s window) still step aside. The marker is a protected rv wiring file, and `rv uninstall` removes it. On Linux without a systemd user manager, observe-mode hooks now ask after a reboot or logout until `rv service start`. Known gap: the agent runs as the same user, so one opaque command that both stops rvd and rewrites the marker still gets through.
- The curl installer now refuses releases rv did not sign. Every download needs a `SHA256SUMS.sig` that verifies against rv's release key (`ssh-keygen -Y verify`, principal and namespace `rv-release`), Linux included, so `ssh-keygen` must be installed. On macOS the downloaded binaries, the Swift runtime dylib and RVApprovals.app must carry a valid Developer ID signature from rv's team (`5V273URY46`), and Gatekeeper must accept every one but the dylib as notarized. A signature by another key or another team, or a `SHA256SUMS` changed after signing, is always refused. An unsigned file or a missing `SHA256SUMS.sig` is refused unless `RV_INSTALL_ALLOW_UNSIGNED=1`. Releases before 0.2.2 have no `SHA256SUMS.sig`: on Linux, installing one with `RV_INSTALL_VERSION` needs that override; on macOS this installer refuses them outright, because their Swift runtime dylib is signed by the Swift project's team (use the `install.sh` attached to that release). Before, `install.sh` trusted whatever `SHA256SUMS` the release served and only warned about unsigned files.
- macOS curl installs need to reach Apple. Gatekeeper looks up each downloaded binary's notarization ticket online (a bare binary cannot carry a stapled one), so on a Mac that is offline, or whose proxy blocks Apple's notarization service, the installer refuses with `Gatekeeper does not accept <file> as notarized`. `RV_INSTALL_ALLOW_UNSIGNED=1` does not skip this check.
- The installer checks rv's team with a code requirement (`codesign --verify -R`: an Apple anchor, the Developer ID intermediate, a Developer ID Application certificate, and `5V273URY46` as the certificate's OU) instead of reading `TeamIdentifier=` from `codesign -dvv` text.
- The shared launcher resolver now sees through transparent exec wrappers (`setsid`, `stdbuf`, `ionice`, `chrt`, `taskset`, `flock`, including `flock FILE -c CMD`, `unbuffer`, `caffeinate`, `nocache`, `numactl`, `prlimit`, `chpst`), parsing each one's options and leading operands. Redirects never fill an option value or operand slot, and a variable or glob there is judged unmodelled. `firejail`, and `chpst`'s environment, root and directory options, are never treated as transparent. Before, `setsid rv uninstall` or `stdbuf -oL rv packs disable core.git` slipped past the self-protection floor, and the same wrappers hid commands from the other floors that use the resolver. A wrapper option rv does not model fails closed: every later operand is judged as a possible command.
- An observe host now sends to Terminal a command whose program rv cannot see, under its own rule id `observe.floor:unanalyzable`: a dynamic command word (`$x`, `$(…)`, backticks), a dynamic `eval` (`eval "$(echo <base64> | base64 -d)"`) or `trap` action, a shell or interpreter reading its program from stdin unless every command feeding it is a literal `echo`, a plain `printf`, a `cat` of literal paths or a literal heredoc (so `… | base64 -d | sh`, `… | sed 's/^/launchctl /' | sh` and `python3 -c "print(…)" | sh` all count; inside an `if`/`for`/`case`, a group or a function body every other command of the text counts as a producer and must print whole lines), and a literal feed is itself read: the text a shell or interpreter gets from a literal pipe, here-string or heredoc is scanned like the line and read by the stop and install floors (`echo 'echo <b64> | base64 -d | sh' | sh`, `sh <<< 'launchctl bootout …'`), with wrappers seen through on both sides (`command`, `env`, `sudo`, `exec`, `nohup`, `time`, `nice`, `stdbuf`, `caffeinate`, `arch`, `xcrun`, `X=1`) and command names matched unescaped, case-folded and by basename (`\sh`, `Bash`, `/BIN/SH`); Anything else that names one stays enforced, and every command that names rv's config directory stays enforced, read or not. The proof reads every Unicode scalar of the command and accepts only ASCII letters, digits, space, tab and the characters `.` `_` `/` `~` `=` `:` `,` `+` `@` `%` `-` `;` `&` `|`, so a line break, a CRLF, or a combining mark or joiner glued to a separator or redirect is no proof.

It compared Swift Characters, and a combining mark, joiner or prepended character joins the next or previous byte into one Character that is not `;`, `|` or `>`, while the shell still reads that byte: `echo hi \u{600};rm -rf build` entered the lane as one `echo` (judge waived; the packs still ran), as did `echo hi >\u{301} out`. The observe floor reads a reader's stdin only when it has one unambiguous source (a pipe, or a single literal here-string, heredoc or file on fd 0, and no other input redirect), since shells combine redirects differently: a second input, a numbered, named or duplicated input redirect, or a script operand naming a descriptor (`/dev/stdin`, `/dev/fd/3`, `/proc/self/fd/3`, `awk -f -`) is unreadable and goes to Terminal, harmless ones included (`sh 3</dev/null < script.sh`, `echo ls | sh </dev/null`), and a here-string handed to a script operand is read like a program. ### Added

- Audit mode for an MCP server's egress allowlist: `"sandbox": {"hosts": [...], "enforcement": "audit"}` in mcp.json lets a host outside `sandbox.hosts` through and writes an fsync'd `egress.observed` audit event for each one (`rv audit tail --kind egress.observed` lists them); if that event cannot be written, the request is denied. The event is written after the SNI check and before the dial, so it means "admitted past the host list"; a following `egress.denied` for the host means the request still failed. Each server may make 60 audit passes a minute; past that, requests are denied `denied-policy`. Audit relaxes only the host list: the proxy credential, port, IP-literal and loopback refusals, SNI binding and the public-address dial filter still deny, and an audited host never gets another host's `allowed_ips`: it dials public unicast only. `enforce` is the default; any other value, or `audit` without `hosts`, makes mcp.json invalid. Audit takes effect only in an mcp.json rv trusts and never under an organization policy. `rv mcp trust` of such a file first records a `config.changed` loosening event and refuses with exit 74 when the audit log cannot take it. `rv mcp list`, `rv mcp check` and the `rv mcp trust` review name every server in audit mode.
- Per-endpoint private ranges for MCP sandboxes (MCP sandbox proxies on macOS and Linux 6.7+; port 443): `"sandbox": {"hosts": ["staging.corp.lan"], "allowed_ips": {"staging.corp.lan": ["10.0.5.0/24"]}}` lets that one listed host reach a LAN service (a staging box, an internal API) through the server's egress proxy without opening private ranges in general. A name resolving to a non-public address is relayed only when every address it resolves to is inside that host's list; a partly covered answer is refused whole, and the proxy connects the exact address it checked, from one lookup. Loopback, link-local, cloud metadata and platform hosts (169.254.169.254, 100.100.100.200, 168.63.129.16, 192.0.0.192, fd00:ec2::254, fd00:ec2::253, fd00:ec2::123, fd20:ce::254), multicast, unspecified, documentation, benchmarking and the IPv6 forms that embed an IPv4 peer (NAT64, 6to4, Teredo, compatible, translated) never open: an entry that touches one, a malformed or scoped entry, or a range for a host not in `sandbox.hosts` refuses the whole mcp.json. IPv4-mapped IPv6 is judged as its IPv4 address and scoped IPv6 answers are refused. The proxy refuses answers equal to this machine's interface addresses (a per-dial snapshot; other routes to the host, such as a Docker or Lima host gateway, are not detected); if the interfaces cannot be listed, private-range dials are refused. - Caged (Seatbelt) runtimes start with core dumps off and capped open files (default 65536) and file size (default 64 GiB; a larger write gets `SIGXFSZ`, or `EFBIG` if the signal is ignored), plus an optional CPU cap, from a new strict `limits` object in `runtime-resources.json` (`openFiles`, `fileSizeBytes`, `cpuSeconds`, `timeoutSeconds`; unknown keys or out-of-range values refuse the file). Limits only ever lower what rv inherited; a limit the kernel refuses stops the launch. `cpuSeconds` is enforced by rv, per process: macOS only signals `SIGXCPU` for `RLIMIT_CPU`, so a watchdog outside the cage kills a process that passes it. A fork starts its own count, so forking resets the cap. `rv workspace run --timeout <N|Ns|Nm|Nh>` (capped by `limits.timeoutSeconds`, which is also the default) ends the runtime at the deadline, records `runtime.ended` with reason `timeout`, and exits 124 with `rv: runtime stopped after its N-second timeout` on stderr, naming the host's deadline. 124 with that line is rv's deadline; a runtime that itself exits 124 passes through without it, and any other SIGKILL keeps its status. With the host gone, a process that forks and calls `setsid` can escape the watchdog, the CPU cap and the group kill, and a tracked process that execs a setuid binary is dropped. - `rv policy rollback <revision> [--repo] [--save] [--json]` restores an earlier revision from the verified revision log as a new head. Without `--save` it only previews: the revision being restored and the current head (number, content hash, recorded time), the effective-rule diff, and the risk findings. `--save` asks for device-owner approval like `rv policy apply --save`; a restore that drops or relaxes a deny or ask, downgrades safety, or widens secret exemptions is refused with exit 2, and a forged or missing log or an unknown revision refuses with nothing written. The save is bound to the previewed revision and head: if the policy changed after the preview it refuses (`headChanged`, "policy changed since preview") without rolling back, and rolling back to the current head reports `unchanged` without an owner prompt. - Gate changes are audited: `policy.changed` (machine and repo `policy.toml` saves and rollbacks, with revision, hash, rule count and the prior revision), `config.changed` (safety level, `guard.hosts`/`guard.mode`, packs, allowlist, `secrets.json`, `rv egress approve|deny`, the policy ceiling, with prior and new value) and `policy.managed` (an accepted organization serial, or a bundle that stops verifying, is removed, or changes) land in `audit.jsonl` with `authorized_by` (the owner check that passed, the organization signature, or `none`). Rule ids, secret names and hosts only; never command text, secret values or policy bodies. The event is written before the change. When the audit log cannot take it (unwritable, or its lock not free within a second), a change that only tightens the gate is still made with a stderr warning and a late record, and anything that loosens it, mixes both or cannot be classified is refused with exit 74 (`EX_IOERR`). Known limits, not guarded: a nested agent started with servers rv does not govern (`claude --mcp-config …`, `claude --plugin-dir …`, `codex -c mcp_servers…`), and a program that writes a config without its command line visible as text: a script or scheduled job written to disk earlier (by the shell or the file tool), a shell fed an expansion (`echo "$CMD" | sh`), text decoded or rendered by a program (`base64 -d`, `rev`, `tr`, `printf 'cla%sude mcp add x' u`), output joined across commands other than `echo`/`printf`/`print` (`{ cat <<<'claude '; cat <<<'mcp add x'; } | sh`), Claude Code's native build reached through the working directory, a variable or a renamed copy (`cd …/claude/versions && ./2.0.14 …`, `$D/versions/…`), a tarball, directory or URL whose name the agent chooses, or a git hook (which `git commit -m` still runs), diff/pager tool, `.ackrc` or lesskey file set up earlier. A host name or a value rv cannot read after the options of a program rv does not list as a runner is read as the start of the command it runs, so a dynamic group word or head there asks (`strace -f claude $SUB add`, `strace -o log $C mcp add`). ### Fixed

- One stuck MCP server no longer hangs `rv mcp serve`'s client. A server that does not answer `initialize` within its `startTimeoutSeconds` (a new mcp.json field for local and remote servers, whole seconds from 1 to 600, default 60; the failure names the setting) is stopped and counted failed (the reason is on stderr and in its calls' "unavailable" error), and requests that were waiting for every server to start go ahead without it. Until every server has settled (answered `initialize`, failed, or passed its `startTimeoutSeconds`), every `tools/list` and `tools/call` waits, so one slow server's start limit holds back every tool; a server that fails to start stays failed for the session (it is not restarted, see below). A server that answers `initialize` with an error is now stopped too; it was left running. A `tools/list` page a server does not answer within 30 s (a limit that cannot be configured) ends that server's part of the listing with the pages it already returned, and the server is asked to cancel it; it stays ready. A `tools/call` with no answer within its server's `callTimeoutSeconds` (a new mcp.json field for local and remote servers, whole seconds from 1 to 86400, default 300; each progress notification rv passes on for the call starts it again, but never past 10 times `callTimeoutSeconds` from when the call was forwarded, 50 minutes by default, so a tool that legitimately runs longer needs a larger `callTimeoutSeconds`) gets a `-32603` error naming the server, the tool and the limit, an `mcp.call` audit record with outcome interrupted and reason "timed out", and a `notifications/cancelled` to the server: rv asks the server to cancel and stops waiting; it cannot make the server stop. The call is never sent again, and a late answer is dropped. This covers remote servers too, including a legacy SSE server that accepts a call (202) and never answers it on its stream. Unanswered approval prompts now expire on time instead of on the next message. A client's cancel of a forwarded call ends its audit trail with one interrupted record (reason "cancelled by client"); a cancel of a request still waiting for the servers to start removes it, so it never runs. These limits run on a clock that stands still while the machine sleeps and that setting the time of day does not move, so waking does not time out every call at once and a clock set back does not hold a call open. On a streamable HTTP server rv's own deadline is the one that fires: the HTTP layer waits a minute past every limit rv sets for that server, a request it gives up on is not answered as if the server had (so it is never recorded as run), and a call or list page rv cancels has its POST closed, so it holds no connection; a cancelled call waiting on a token refresh is not sent again with the new token. A connection that fails under a request is not the server's answer either: the server counts as gone, and its calls are recorded interrupted (they may have run), never as run. On Linux each POST to a remote server now goes on a connection of its own: libcurl sent a request again, without its body, when a kept-alive connection dropped before its answer, so such a call hung until the HTTP limit instead of failing at once (and could have reached the server twice); on macOS connections are still reused. Stopping a local server sends SIGTERM, then SIGKILL 2 s later if it is still running (before, SIGKILL at once), without holding up the gateway; both go to the server's whole process group (see below), not to what it started in a session of its own or outside rv, such as a `docker run` server's container.
- One MCP client or server that stops reading no longer stalls `rv mcp serve`. Each destination (the client, each local server's stdin, each remote server) is written by a thread of its own, so the gateway goes on serving everything else while one destination is slow. A local server with more than 128 MiB waiting for its stdin (two of the largest lines rv passes on, 64 MiB), or a remote server with more than that sent and not yet taken (counted until its request body has all gone out, or its POST is over if that comes first; its POSTs run side by side, started in order), is stopped, with one line on stderr, and its calls fail as on any exit. The client has no byte bound: what rv writes for it, counted in written (escaped) bytes, holds back the reader whose line produced it until written, so a server flooding the client slows that server only, and a `notifications/tools/list_changed` is not queued for the client while another waits. rv's own messages to the client (the errors for deadlines and exits) are always queued. A client that takes nothing of what waits for it for 30 s (on the clock that stands still in sleep; rv writes at most 1 MiB at a time and counts each write that returns as progress, so a client on a blocking pipe that takes at least 1 MiB in every 30 s, about 35 KiB/s, is not taken for one that stopped; a slower one is) ends `rv mcp serve` with exit status 1 and one line on stderr; serve stops handling its requests then. Shutdown and cancels get through while a write is stuck, and a full non-blocking output is waited on, so no line is left half written. The client's reader and each local server's stdout reader stop reading once 64 MiB of its lines, or of their output for the client, wait, so a local server or client writing faster than the gateway handles its lines no longer grows memory without bound. A remote server is not slowed down that way (its connection goes on reading, on macOS and Linux alike): what it sends waits for the gateway off its connection, and once more than 128 MiB of it waits, rv stops the server, with one line on stderr, and its calls fail as on any exit. A streamable HTTP reply larger than 64 MiB, or one of its events larger than that, ends only the call it answers, with an error naming the limit it passed, and the server stays connected (on Linux too, where the reply's end was taken for one without an answer); such an event on a legacy SSE server's stream still ends that stream, and the server is restarted. An event-stream reply is closed once its answer is in, so a server that answers and holds the stream open holds no connection. A remote server has at most 64 calls in flight: past that a call is refused unsent ("already has 64 calls in flight", audited as not run), and nothing in flight is touched. A client's cancel that lands while part of the call's reply is being read closes only that call; it could take the server for gone and restart it. A 401 retry's body counts against the 128 MiB as the first try's did. Each remote server has about 160 requests of any kind in flight at most (its 64 calls, a cancel for each, and room for listings, pings and notifications; on Linux each is a connection, so several saturated remotes add up; a 401 retry or a legacy SSE server's first messages can pass it briefly): past that a request is not sent, a call ends not run with an error saying so (an approved one is recorded declined, and its approval is used up, so it must be approved again), a listing page fails, a notification is dropped with one line on stderr (a cancel still closes the request it names), and nothing in flight is touched. rv's own ping is never held back by the limit (there is one at a time), so a full remote can still be found hung. A notification's (or reply's) POST is let go at most 30 s after it is sent and 5 s after its response starts, whichever comes first, on a timer of rv's own, so a server that holds it open or drips bytes cannot keep it; a normal response ends first and is never cut, and a 401 or 404 in it is acted on as before. rv's own stderr lines go through a 1 MiB buffer: when stderr is not being read, the lines past it are dropped and counted, and the count is written with the next line that fits. Stopping a remote server, and its session DELETE, no longer hold up the gateway.
- An MCP server that goes away mid-session is started again. A local or remote server that was ready this session and then exits, ends its session (HTTP 404), loses its connection under a request, stops reading its input past its bound, or stops answering (no answer to rv's own `ping` within 10 s after one of its calls timed out; one ping at a time, and its answer is never passed on) is started again after 1 s, then 2, 4, 8 and 16 s, at most 5 times in any 10 minutes; past that it stays failed for the session, with the reason on stderr, until the MCP client restarts `rv mcp serve`. The 10 minutes slide: a server that goes away about every two minutes, or less often, is restarted for as long as serve runs, and its secrets are resolved again each time (which can mean a secrets provider's unlock prompt each time). A server that handles one request at a time and is still busy with a slow call cannot answer rv's ping either, so it is stopped too, and whatever it was still running is cut off. A server that was never ready (it failed to start or to initialize) is not restarted. Nothing in flight is sent again: each call waiting on the server ends with one `-32603` error saying it may have run and one interrupted audit record, a prompt it held is declined, and a call that arrives while it is being brought back is refused at once ("rv is restarting it"), not queued, and audited as not forwarded. A prompt accepted while its server restarts, and a prompt the client cancels, are audited as declined. A restart must start and answer `initialize` within `startTimeoutSeconds`, or it counts toward the restart cap; that time counts from when rv has reaped the server's last process, so rv's own wait for it (up to 7 s) does not use it up. A restarted server is initialized and listed again before any call reaches it (a listing that fails, times out, whose cursor cycles, or that is not complete within four list pages' time, 2 minutes, stops it again, and counts; only names rv would serve are kept from it), so a tool whose definition changed is handled as any mid-session change (it asks, and is hidden until `rv mcp trust`), and an approval for the old definition does not carry over. After rv restarts an MCP server, only tools that server lists again can be called; others are refused and audited. It is started from the mcp.json `rv mcp serve` verified at start, not read again from disk: the same command, arguments, environment and cage, its secrets resolved again, a placeholder server leased afresh once its old group is reaped and its old lease revoked, and a sandboxed server's egress proxy replaced (a plan that fails, or whose launch then cannot be started, stops the proxy it started at once). One server is never started twice at once. Once serve is stopping, a restart still waiting for its last process to be reaped plans nothing; one already past that wait (planning, or about to) is not interrupted, and what it plans is abandoned when it returns (an unlock prompt, say): nothing is started, its lease is revoked and its proxy stopped. A restart that would start after its `startTimeoutSeconds` ran out starts nothing, even in the second before rv's own timer sees it, and is stopped if it did. The client gets `notifications/tools/list_changed` when the server goes away and when it is back, if it was told tools exist. Every local server now runs as the leader of a process group of its own, and serve counts it gone once it is reaped, not when its stdout closes, so a launcher whose child keeps stdout open no longer looks alive; a stop signals the whole group, and only while its leader is not yet reaped. An answer a server wrote just before it exited that rv has not read 1 s after its reap is dropped, and that call is recorded as may have run. A launcher that starts the real server and exits now counts as the server exiting: its group is killed and it is restarted under the cap. As a group leader a server cannot call `setsid()` itself (its children can). A terminal's Ctrl-C, a closed terminal's SIGHUP, or a host's process-group kill reaches serve but no longer the servers, so every `rv mcp serve` now catches SIGINT, SIGTERM and SIGHUP and stops its servers itself (a second signal kills what is left at once; serve exits 128 plus the signal). A signal while serve plans its servers ends it at once, as killed by that signal, however long a secret provider or unlock prompt holds the plan: no server is started, the proxies planning started are stopped and its leases end. On Linux, a serve that cannot set up how it hears signals refuses to start rather than run without them, and a serve started with these signals blocked (a parent thread's mask passes to its children) unblocks them, so it still hears them; before, only a serve with a placeholder server did, and any other died at once, leaving its servers running and its calls without their last record. A server starts with every signal at its default, even one rv inherited ignored (`nohup`'s SIGHUP): rv decides when it stops. A SIGCHLD that serve inherited ignored is set back to the default, so its servers' exits are seen and their groups killed. On Linux a server inherits only descriptors 0, 1 and 2 (closed in the child after the spawn, so one another thread opens meanwhile is not passed on; needs glibc 2.34, below rv's 2.35 floor), and rv's egress proxy opens its sockets close-on-exec. What a server started in a session of its own (`setsid`) or outside rv (a `docker run` container) is still not reached, and such a child holding the server's stdout keeps one of serve's threads until it exits. When serving ends (the client closes its input or stops reading, or serve gets a signal), each call still in flight gets one interrupted record ("gateway stopped; the call may still have run") and each prompt still shown is recorded declined, before serve exits.
- A caged (`sandbox`) MCP server may hard-link files only among its write directories (scratch, temp, `~/Library/Caches`, `~/.npm`, `~/.cache`, `sandbox.writable`), and may neither link nor clone a credential path; before, the profile left `file-link` and `file-clone` to `(allow default)`. Linking a file the cage could not write was already refused on macOS 27. A directory from outside its write directories can no longer be cloned whole (`clonefile(2)` copies the entire tree and Seatbelt checks only its top, so cloning `~/.config` copied `~/.config/gh`), and a credential's ancestors inside its write directories, as the profile finds them at launch, can be neither cloned, renamed nor removed; one that is a symlink is named at the link as well as at its target, and so is a link a `..` in a credential link's target steps out of, so neither can be swapped for a link elsewhere. One that is missing cannot be created by the cage, as a symlink, a renamed link or directory, a hard link, or a plain directory (`mkdir -p` through a missing `~/Library/Application Support/Google` fails when the home is a write directory). A link (the credential or a directory above it) retargeted by a process outside the cage while the server runs leaves the new target readable until restart. ### Security

- On Linux the secrets gateway refuses a request head with a bare CR or LF followed by a combining mark; Foundation's Unicode-aware match had let it into a header value. Found by libFuzzer.
- The self-protection guard now refuses an `env -S`-shaped option spelled through a variable, substitution, glob or replace string ahead of `xargs` stdin. Examples are `-$'\x53'`, `-$X`, `-$(printf '\x53')`, `-?`, `--s*`, and `-%` with stdin starting `S`. In observe mode these could run a stdin-chosen `rv` command. Expected false refusals: `-t%`, `-o%`, `-j$(nproc)`, `-j$N` or `-e*` before the replace string.
- The self-protection guard now sees rv admin commands an agent runs where the launcher parser cannot follow, in observe mode too: an interpreter or runner script (`perl -e`, `python3 -c`, `node -e`, `awk`, a sed `e` command, `su -c`, `ssh host cmd`, `watch`, `tmux new`, `fd -x`, `crontab -`), a `find -exec`/`-execdir`/`-ok`/`-okdir` command, and a program a shell or interpreter reads from stdin (`echo '…' | sh`, `| bash -s`, `sh <<< '…'`, `| sudo -s`, `source /dev/stdin`). Script text is scanned as opaque text: a literal rv binary plus an rv verb or weakening flag floors the command at "run it in Terminal", so a one-liner that only mentions `rv policy` in a string is floored as well.
- The self-protection guard now floors every code-shaped `rv allow-once <code>` from an agent at "run it in Terminal". Before, it caught only digit codes, so a real hex code such as `rv allow-once a1b2c3` passed the guard; `rvd`'s owner check still stopped the redemption. The guard applies the CLI's own check (trim, lowercase, `AllowOnceUnlockCode.isValid`), and digit-only words stay flagged as before.
- MCP tool rug-pull defence: only `rv mcp trust`, with you present, pins upstream tool definitions, in `~/.config/rv/mcp-tool-pins.json`, MAC'd with the approvals key that signs mcp.json. A pin is the hash of the whole tool object (name, description, title, annotations, input and output schema, `_meta`, icons, any other field). `rv mcp serve` never pins: it queues each definition that matches no pin in `~/.config/rv/mcp-tool-review.json` (unsigned, at most 1 MiB and 512 entries, and at most 256 KiB and 128 entries per server, so one noisy server cannot keep another's tools out; a full queue drops new entries, says so on stderr, and offers them again on the next listing) and says once per start on stderr how many tools on each server are not yet trusted. `rv mcp trust` shows every field of every queued definition, display-escaped, pins exactly what it showed, and drops queued tools of servers no longer in mcp.json; if the pins on disk changed during the review it pins nothing and asks you to run it again. An unreadable pins file does not stop `rv mcp trust` from signing a changed mcp.json: it says pinning was skipped and why, and leaves the pins alone. A missing, unreadable, or unverifiable pin store pins nothing, so deleting the file can only make tools ask. A tool that is not pinned (new, changed, or not checkable, including one listed this session with any definition other than its pin, even once) is never called under `allow` for the rest of the session: it asks, and it is listed with no upstream text but its name: rv's marker (the tool changed or is not yet trusted, and its description and parameters are hidden until `rv mcp trust`) as its description, `{"type":"object"}` as its input schema, no output schema, and of its annotations only `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint` with boolean values. An approved call still forwards the client's arguments unchanged. A tool whose upstream name is not 1 to 64 of `A-Z a-z 0-9 _ . -` is neither listed nor callable, pinned or not, and is not queued; stderr names one such tool, escaped and truncated, once per server per start. Each not-pinned definition writes one `mcp.tool.changed` audit event, at most 64 per server per session, then one event saying further changes are suppressed. An approval is bound to the definition it was shown for. `rv mcp approve` says when a tool asks because it changed or is not yet trusted, and `--always` on such a tool approves once and points at `rv mcp trust`. A corrupt or oversized review queue is treated as empty and never blocks `rv mcp trust`. On Linux, where any same-user process can read the approvals key (rv does not honor approval grants there either), nothing is pinned and every MCP tool asks. Known limits: a running `rv mcp serve` keeps the pins it started with, so after `rv mcp trust` tools keep asking until the MCP host restarts it (trust says so); restoring an older signed pins file restores the tools you trusted then, until the approvals custodian keeps a counter; a pinned tool's schemas keep vendor keywords (`markdownDescription`, `x-*`, `$comment`), property names and `default`/`examples` as the upstream sent them (you saw them, escaped, in `rv mcp trust`), and `rv mcp trust` does not cap how long a field it shows may be, so a very long field or whitespace run can push the rest off screen; `mcp.tool.changed` has no OCSF mapping yet; JSON objects whose keys differ only by Unicode normalization (NFC/NFD) count as duplicate keys, so such a message is dropped.
- `rv mcp serve` forwards an upstream's progress notification only for a call that upstream is running with the client's `progressToken`, rebuilt from `progressToken`, `progress`, `total` and a display-escaped `message` of at most 512 bytes; any other progress is dropped. An upstream's `initialize` error text goes to stderr only; the client is told the server failed to initialize.
- `audit.jsonl` appends wait at most 2 seconds for another process holding the file lock, then fail with nothing written, instead of blocking every writer behind a stuck one. `rv mcp serve` refuses a call it could not audit, as before.
- The secrets gateway could hand one request's upstream answer to another client. The first requests a gateway forwarded, when they arrived within about a millisecond of each other (an agent or MCP server opening parallel connections as `rv run --secret` or `rv mcp serve` starts), could each build an upstream session of their own. Those sessions numbered their requests alike, so one answer could reach the wrong client, scrubbed only of that client's secret, and the others waited forever, each holding one of the gateway's 64 connection slots. Each request in flight now has an upstream session of its own, and requests are told apart by the request itself, not its number. On macOS a session that served its request to the end is kept for a later one (at most 64 are kept) and released when the gateway itself is deallocated; `stop()` alone does not release it.
- A client of the secrets gateway that stops reading no longer stalls every other upstream answer, and what waits for it in memory is bounded. Each answer is written by its own connection's thread, from an upstream session of its own. On macOS, where a session stops reading while its callback waits, a slow client slows its upstream to its pace: at most about 4.2 MiB waits for it, and it gets an answer of any size, sent once, unless it takes more than 300 s over 256 KiB (the session's request timeout fires while its callback waits) or the transfer passes 3600 s; both cut it short, with no terminator. 16 answers of 256 MiB whose clients stopped reading for 20 s held 103 MiB resident throughout and all arrived whole (64 held 374 MiB, peaking at 762 to 821 MiB once all were read at once). On Linux, where the session goes on reading, at most 64 MiB of an answer waits for its client, and beyond the first 1 MiB of each answer at most 256 MiB waits across all clients (320 MiB with the gateway's 64 connections). An answer that would pass the first fails; when the second is full, the request holding the most fails, even if its upstream has finished. A failed request's upstream request is cancelled and its client's answer ends cut short, without the chunked terminator. So on Linux an answer over 64 MiB from an upstream faster than the gateway forwards it (144 to 373 MB/s on loopback) is cut off: a 256 MiB answer from an unthrottled loopback upstream was cut off after 32 MiB. Before, both systems cut a client off once 8 MiB waited for it, which cut off even a client reading as fast as it could from a fast upstream; the claim that a client keeping up got an answer however large was wrong. The upstream is never suspended. On Linux, suspending dropped the transfer and resuming sent the request again, secret included. On macOS, the session went on reading a suspended request, so suspending bounded nothing and held more memory. A client the gateway has bytes waiting for must take in at least 16 KiB over every 30 seconds the gateway spends writing to it (one blocked write can stretch a window to about 60 s, so the slowest client kept takes in about 273 bytes a second), or it is cut off, its upstream request cancelled and everything it held given back; time spent waiting for the upstream does not count, so an SSE stream between events stays open. Before, each write that moved a few bytes started a 30 s timeout again, so a client taking 1 KiB every 29 s held a slot, two threads, a session and an upstream connection with no limit. The chunked terminator is written only after every byte before it, so a client whose last chunk could not be written no longer gets an answer that looks complete but is missing its last bytes.
- The secrets gateway no longer sends a request again when the upstream drops the connection, on Linux. libcurl re-sent a request on a reused connection that dropped before an answer, and a request with a body went again without it and then waited 300 s for it, holding a connection slot. Each Linux request now has a connection of its own (and its own TLS handshake). On macOS a POST, PUT, PATCH, DELETE or OPTIONS is sent once, but a GET or HEAD is still sent up to three times, credential included, on a dropped connection: Darwin's URLSession does this whatever the request says, and has no setting to stop it.
- The secrets gateway no longer sends a request again, body and brokered credential included, when the upstream answers `401` with a `Basic` or `Digest` challenge, on macOS. Darwin's URLSession answered such a challenge by sending the request again, whatever its method; a `Bearer` challenge or a bare `401` was sent once, as was every `401` on Linux. The gateway's upstream sessions now cancel every credential challenge, a proxy's `407` included, which also keeps default handling from offering the upstream an ambient credential such as a Kerberos ticket, and keep no credential storage; the server's certificate is checked as before. A server's request for a client certificate is declined, so no keychain identity is offered; a server that only asks for one still answers. When Darwin gives a cancelled challenge no response, the gateway uses a `401` of its own making, so the audit can record an upstream `401` the upstream did not send. The client gets the gateway's `502` for a rejected brokered credential, as for any `401`, and the audit records the upstream's `401`. The title of commit a4d6069a, "nothing is sent twice", was wrong for a macOS GET or HEAD on a dropped connection and for these challenges.
- Any local process could hold all 64 of the secrets gateway's connection slots, leaving every agent request with `503 gateway busy`, by sending request heads a byte at a time. Each read waited up to 30 seconds with no overall limit, and all of this came before the gateway checks which process is connecting. A client now has 10 seconds from being accepted to send its request head, and 60 seconds for its body once the head has been accepted; past either deadline it is answered `408` (`requestTimeout`) and its connection is closed. That alone left an outage open: a process reconnecting every 10 seconds could still hold every slot. So the gateway now checks which process is connecting before it reads a byte. A connection from outside every registered runtime holds none of the 64 slots; it takes one of 8 of its own, with 2 seconds for its head, and past those 8 it gets `503 gateway busy` unread. It is never forwarded. A live placeholder it presents raw, or inside `Basic` credentials, on a route and with a method the gateway serves is looked up, and the refusal names that placeholder's runtime (`runtimeMismatch` once the placeholder passes its own policy). A refusal made before any lookup names no runtime: one of an echo method such as `TRACE`, or of a percent-encoded placeholder (`encodedPlaceholder`), names only the secret its path names, and one of an unknown route names neither. The check itself now runs before a connection takes any slot, at most 8 at a time, with the next connection waiting unread and up to 128 more in the listen backlog: before, an outsider held one of the 64 slots while its process scan ran, so outsiders slow to tell apart could hold all 64 and have runtimes answered `503`. Outsiders can now delay a runtime's request, and the gateway no longer turns it away for them, except a runtime's connection whose process cannot be placed when it connects: that waits as an outsider, with the outsiders' 8 slots and 2-second head deadline, and gets `503` while 8 outsiders hold them. A burst of a runtime's own connections also waits behind the checks, 8 at a time (the cost of one check was not measured); a flood that fills the listen backlog of 128 still has the kernel refuse new connections, or drop one after its `connect` returned, a runtime's included, until it dials again (seen on macOS with 16 threads connecting and resetting at once). No flood test turned a runtime away on the earlier code either (5 of 5 passes there), and none could: the test's 16 threads each hold at most one connection at a time, not the 64 slots, so it shows only that a runtime is answered through such a flood now. That outsiders turned a runtime away before was shown by outsiders slow to tell apart. A connection whose process cannot be placed at all waits as an outsider, and the full check after its head decides; before, that first look alone refused it. Refusals from outside every runtime are recorded at most once a second, with how many were left out since the last record, so outsiders cannot write audit records as fast as they like: every `malformed` or `requestTimeout` refusal, whatever its head holds, since it is refused before its head is checked for a live placeholder, and an `unknownRoute` refusal or any refusal of a request naming a secret, a made-up one included, unless its head presents a live placeholder, raw, percent-encoded or inside `Basic` credentials; one that does is always recorded. The last one left out is written when the gateway stops; with neither a later refusal nor a stop, that count is not written. A refusal still being made as the gateway stops is written as it comes, and a gateway started again never writes an earlier run's count. A client resetting its connection before the gateway accepted it no longer stops the gateway accepting connections. One resetting it just after, before the gateway set it up, is now closed unanswered: Darwin refuses `SO_NOSIGPIPE` on such a socket, and the gateway's answer to it raised SIGPIPE, which ends any process hosting the gateway that does not ignore that signal: rv-workspace-host and `rv mcp` ignore it, but the `rv` process of `rv run --secret` does not, and could be ended this way before. rvd does not host the gateway.
- A local process that connects and resets its connection before an answer can no longer end the process answering it with `SIGPIPE`, on macOS. A socket whose peer is gone refuses every socket option, `SO_NOSIGPIPE` included, so the answer's write raised the signal. Every such socket write now passes `MSG_NOSIGNAL`: those that relied on `SO_NOSIGPIPE` (the secrets gateway, the egress proxy, the workspace control transport, rvd's listener), and the sign-in redirect of `rv mcp connect`, which set no `SO_NOSIGPIPE` at all and which any local user could end this way before it received the browser's answer. rvd's listener was not exposed: its connections inherit `SO_NOSIGPIPE` from its listening socket, and one whose peer is gone has its receive timeout refused too and is closed unanswered.
- On Linux, the secrets gateway passes over an upstream's interim answer (`100 Continue`, `103 Early Hints`) and gives the client the final one; it took the interim answer as final before. An upstream's `101 Switching Protocols`, which the gateway never asks for since it drops `Upgrade`, fails the request: the client gets `502` saying the gateway does not carry another protocol, and the audit says so too, where macOS handed on the `101` head before. On Linux this was seen only through the gateway's own test with a loopback upstream, in one container run. An answer cut off because the client's write failed is now audited as cut short, as one the upstream ended is.
- MCP tool rug-pull defence: only `rv mcp trust`, with you present, pins upstream tool definitions, in `~/.config/rv/mcp-tool-pins.json`, MAC'd with the approvals key that signs mcp.json. A pin is the hash of the whole tool object (name, description, title, annotations, input and output schema, `_meta`, icons, any other field). `rv mcp serve` never pins: it queues each definition that matches no pin in `~/.config/rv/mcp-tool-review.json` (unsigned, at most 1 MiB and 512 entries, each server in mcp.json getting an equal share of both, so noisy servers cannot keep another's tools out; a full queue drops new entries without rewriting the file, says so once per server on stderr, and offers them again on the next listing without a second audit event) and says once per start on stderr how many tools on each server are not yet trusted. `rv mcp trust` shows every field of every queued definition, display-escaped, pins exactly what it showed, and drops queued tools of servers no longer in mcp.json, also when there is nothing to trust, but only by an mcp.json that matches its signature or that you have just confirmed and signed; if the pins on disk changed during the review it pins nothing and asks you to run it again. An unreadable pins file does not stop `rv mcp trust` from signing a changed mcp.json: it says pinning was skipped and why, and leaves the pins alone. A missing, unreadable, or unverifiable pin store pins nothing, so deleting the file can only make tools ask. A tool that is not pinned (new, changed, or not checkable, including one listed this session with any definition other than its pin, even once) is never called under `allow` for the rest of the session: it asks, and it is listed with no upstream text but its name: rv's marker (the tool changed or is not yet trusted, and its description and parameters are hidden until `rv mcp trust`) as its description, `{"type":"object"}` as its input schema, no output schema, and no annotations (an unreviewed `readOnlyHint` could let a host skip its own prompt). An approved call still forwards the client's arguments unchanged. A tool whose upstream name is not 1 to 64 of `A-Z a-z 0-9 _ . -` is neither listed nor callable, pinned or not, and is not queued; stderr names one such tool, escaped and truncated, once per server per start. The same holds for a tool whose `inputSchema` or `outputSchema` names a property (a `properties`, `dependencies` or `dependentSchemas` member, a `required` or `dependentRequired` entry; a name list of any other shape has every string and key in it checked) with a control, separator or format character: it is still checked against its pin, but it is neither listed nor callable, and `rv mcp serve` does not queue it for review or count it as not yet trusted. Once listed that way it stays refused until a listing shows it with a definition that does not hide a name; a listing that omits it, an upstream error or an upstream exit mid-listing does not clear it, and one hiding entry hides the name even beside a clean one in the same listing (all its pages). On a server that lists such a tool past the 4096 tools rv tracks, every tool rv does not track is hidden and refused rather than asked, also when a prompt for it was already showing (accepting it records that prompt as declined), with its own audit reason; stderr says so once per server per start, and it lasts until `rv mcp serve` restarts. A new or changed such definition writes its `mcp.tool.changed` event with `"hidden": "true"`, and stderr names one such tool once per server per start. `rv mcp trust` does not filter the queue, so a definition an older rv queued is still shown (escaped) and can be pinned; it stays hidden. In a pinned tool's schemas, `$comment` and `markdownDescription` strings are escaped like `description`, and a `title` or `description` (of the tool, its annotations or its schemas) that is not a string is dropped. Each not-pinned definition writes one `mcp.tool.changed` audit event, at most 64 per server per session, then one event saying further changes are suppressed. A session checks at most 4096 tools per server against the pins; any further tool of that server asks (or is hidden and refused, as above), and stderr says so once. A session offers at most 1024 definitions per server to the review queue; a later changed definition of that server is not queued (it still asks), and stderr and one `mcp.tool.changed` event say once that tracking is full for it: restart `rv mcp serve` after `rv mcp trust`. An approval is bound to the definition it was shown for. `rv mcp approve` says when a tool asks because it changed or is not yet trusted, and `--always` on such a tool approves once and points at `rv mcp trust`. A corrupt or oversized review queue is treated as empty and never blocks `rv mcp trust`. On Linux, where any same-user process can read the approvals key (rv does not honor approval grants there either), nothing is pinned and every MCP tool asks. Known limits: a running `rv mcp serve` keeps the pins it started with, so after `rv mcp trust` tools keep asking until the MCP host restarts it (trust says so); restoring an older signed pins file restores the tools you trusted then, until the approvals custodian keeps a counter; a pinned tool's schemas keep other vendor keywords (`x-*`, `enumDescriptions`), `patternProperties` regexes, `$defs` and `definitions` member names, `$ref`/`$id`/`$anchor` strings, and `enum`/`const`/`default`/`examples` values as the upstream sent them, since a client sends those values back verbatim (a control, bidi or tag character in an `enum` value reaches the client as is; you saw it, escaped, in `rv mcp trust`), and every top-level field of a pinned tool other than its name, `description`, `title`, `annotations.title` and schemas (`icons`, `_meta`, other annotation keys, a tool-level `$comment` or `markdownDescription`) is forwarded as sent too, and `rv mcp trust` does not cap how long a field it shows may be, so a very long field or whitespace run can push the rest off screen; `mcp.tool.changed` has no OCSF mapping yet; JSON objects whose keys differ only by Unicode normalization (NFC/NFD) count as duplicate keys, so such a message is dropped.
- `rv mcp serve` forwards an upstream's progress notification only for a call that upstream is running with the client's `progressToken`, rebuilt from the client's own `progressToken`, `progress` and `total` (each a finite number spelled in at most 32 bytes) and a display-escaped `message` of at most 512 bytes; any other progress is dropped. An upstream's `initialize` error text goes to stderr only, display-escaped and cut to 512 bytes; the client is told the server failed to initialize.
- An `audit.jsonl` append waits at most 2 seconds for its locks, the in-process lock and the file lock together, measured on the monotonic clock from when it starts, then fails with nothing written. Each writer queued behind a stuck one gives up on its own deadline instead of waiting its turn first. The in-process lock is per log, by the log's directory and then by the file itself (so an `audit.jsonl` hard-linked into two directories is one log), and an append waiting on one log keeps no other log in the process waiting. On a filesystem that counts locks per process (some network filesystems), an append through a second directory that times out can still drop the holding append's file lock when it closes its file. The deadline covers only those lock waits: creating the directory, opening, reading the tail, writing and `fsync` are not bounded, so a hung filesystem can still hold an append. `rv mcp serve` refuses a call it could not audit, as before.
- `rv mcp serve` builds a tool call's reply from the upstream's `result` or `error` only, so an upstream cannot add fields such as `method`/`params` to it. Every `description`/`title` string inside a pinned tool's schemas is shown with hiding scalars escaped, like the top-level description; `pattern`, `const`, `enum`, `default` and `examples` stay byte-exact. Tool result text is forwarded unchanged: rendering it safely (ESC sequences, bidi overrides, tag characters) is the MCP host's job. rv escapes those scalars wherever it shows or records text itself: approval prompts, `rv mcp trust`, stderr, and `audit.jsonl`, which now writes every such scalar as a JSON `\u` escape.
- `audit.jsonl` refuses an event whose line would exceed the verifier's line limit, instead of writing a line after which every append failed; the `mcp.call` event caps argument names (64 of at most 256 bytes, `argumentKeysTruncated`), the tool and subject (512 bytes) and the reason (1 KiB). `rv report` counts a forwarded MCP call once.
- Linux self-protection: the file-tool door now protects the Swift runtime libraries `rv-cli` and `rvd` load from `~/.local/bin` (`*.so`, `*.so.*`) and install.sh's `.rv*` files, as the shell guard already did, plus `~/.config/environment.d` (read into every user service, `rvd` included), systemd's `~/.config/systemd/user.conf`(`.d`) and `~/.config/systemd/user/service.d` drop-ins, and `rvd`'s `default.target.wants` link. An `rvd` that `rv setup`/`rv service start` runs directly (no systemd user manager) no longer inherits the caller's `LD_*` and other loader variables.
- A comment on an inert command (`ls # …`) is kept, and judged, when the same command can redefine that command name (an alias, function, `hash`, `eval`, `source`, `trap`, or a dynamic command word).
- `system.disk` denies Linux drive-destroying tools it missed: `mke2fs`/`mkntfs`/`mkdosfs`, `blkdiscard`, `sgdisk --zap-all`/`--clear`/`--delete`, `sfdisk` writes, `gdisk`, `nvme format`/`sanitize`, `sg_format`, `hdparm --security-erase`, `cryptsetup luksFormat`/`erase`, `ddrescue -f`, `badblocks -w`, `zpool destroy`, `zfs destroy`.

- Releases can sign `SHA256SUMS` (`SHA256SUMS.sig`, `ssh-keygen -Y`, namespace `rv-release`) with the `RV_RELEASE_SSH_SIGNING_KEY` secret. Once `install.sh` pins the public key, installs refuse a missing (unless `RV_INSTALL_ALLOW_UNSIGNED=1`) or invalid signature; until then Linux installs warn that release signatures are not verified.

- OAuth refresh-token state (`secrets-oauth/*.json`) and the loaded egress snapshot (`egress-loaded.json`) are now written owner-only (0600) with fsync, instead of with the process umask.
- Every hook and file-tool deny and every Policy-gate override (allow-once, allowlist, rebase recovery, contained delete) is now appended to the hash-chained `audit.jsonl` as `command.denied` or `command.override`, so `rv audit verify` covers the gate itself. Events carry the rule, host, tool and a home-redacted path, never command text. Plain allows and contained-workspace (`evaluateAgent`) decisions are not logged yet. The audit export and `rv audit forward` no longer send a deny twice when it is also in `blocks.jsonl`. An override whose `command.override` event cannot be written is not applied: the command stays denied, with a reason saying the audit log could not be written. Such a deny still writes its `command.denied` event (if it can, within what is left of the same 2-second lock wait, so a held lock costs the command one wait, not two) and its `blocks.jsonl` row, unless the hook deadline has passed and no allow-once grant was spent (the hook then answers with its timeout deny), as for any deny row. A deny whose event cannot be written stays a deny. An owner approval whose `owner.action` event cannot be written is refused: no allow-once grant is planted or minted, and the approval is not trusted; the CLI says rvd could not write `~/.config/rv/audit.jsonl` and what to check (new `auditUnwritable` owner outcome, refused like `unavailable`; an older CLI cannot decode it and refuses too). Known limit: that older CLI then says rvd is not reachable and points at `rv doctor`, not at the audit log. For each kind of dropped row (`owner.action`, `command.override`, `command.denied`, `command.observed`) `rvd` writes one stderr line naming the file, at most once a minute per kind; a failed write of that line (a full disk under `rvd.log`) is ignored and cannot stop `rvd`. `rvd` log lines now blank C1 controls and bidi and other format characters as well as C0 and DEL. `rvd` no longer starts without an absolute HOME on Linux (macOS already required one), so it never gates without the owner's policy or with nowhere to record an override or approval. The `owner.action` write no longer runs on the `rvd` request actor, so a stuck audit lock cannot hold up hook evaluation.
- A same-user process can no longer enable or disable packs, save rules or resolve approvals over the SDK socket. Owner mutations stay refused on every generic IPC path; the Python SDK's `set_pack_enabled` now raises `AuthorizationDenied`.
- Contained runtimes (Seatbelt and the macOS guest) can no longer create, rewrite or remove agent and editor config that host tools run later: `.claude/settings.json`, `.claude/settings.local.json`, `.claude/hooks/`, `.mcp.json`, `.codex/config.toml`, `.cursor/hooks.json`, `.cursor/mcp.json`, `.gemini/settings.json`, `.vscode/tasks.json`, `.vscode/settings.json`, `opencode.json(c)` and `.envrc`. - With no judge loaded, a program an interpreter reads from stdin needs the judge in more places: any command a pipe's consumer launches may be the reader (`| eval 'python3 -'`, `| sh -c 'cd /tmp; python3 -'`, `| (cd /tmp && python3)`), not only the first; any command of a group, subshell or payload before the pipe may write the program (`{ curl -s x; echo 'print(1)'; } | python3`), while at the line's top level only the last command of a list does (`cd repo && echo 'print(1)' | python3` stays a packs-only allow); a top-level writer holding an ANSI-C `$'…'` word is read with the rest of its segment; words after `-`, `/dev/stdin` or `/dev/fd/0` are the program's arguments, not a script or an inline program (`python3 - arg`, `python3 - -c x`, `osascript - arg`); a `$'python3'` head counts; an option's separate value is no script operand (`python3 -W ignore`, `node -r dotenv/config`, `ruby -r json`, `lua -l mod`, `php -d k=v`, `perl -I lib`) and never a redirect (`python3 -W <<< …`); and deno and bun given `-`, `awk -f -` (fed by a pipe, here-string, heredoc or `<` file), an interpreter `xargs` runs with no script operand (`xargs python3 -c`) and `osascript` with no script file or given `-` (markers: `do shell script` with any whitespace or a `\t`/`\n` escape between its words, JXA's `doShellScript`, a raw `«event …»`, Terminal's `do script`, `run script`, `NSTask` and `NSAppleScript`) read one. A pipe into `bash` or `zsh -s` is not this floor's: the shell text is unwrapped and analysed as a command. `… | awk -f - <<< '…'` reads the here-string, not the pipe, as the shell does, so the here-string is the program judged.
