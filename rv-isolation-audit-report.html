rv (Rykan V) — codebase, UX, bugs & Isolation audit

Hook-grade shell guard for coding agents, plus a macOS Seatbelt-contained workspace runtime (rv opencode / rv workspace). This audit covers the whole product with depth on RVIsolation: what the sandbox actually guarantees today, where it leaks, and what a user experiences when it refuses.

Date: 12 Oct 2026 Tree: main @ 04b4740c + large uncommitted working tree (45 files, +7,412 lines) Toolchain: Swift 6.4, macOS 27 arm64 (audit host) Method: source inspection of every RVIsolation file, CLI probes against .build/debug/rv, focused test run, and the repo’s own acceptance/adversarial records

Verdict — NOT SATISFIED for Isolation as a finished boundary. Ship the hook guard; do not sell the cage as complete.

Top finding: On macOS the contained launch is a real deny-default Seatbelt fence — workspace-only file access, loopback-only networking through a host-side proxy, same-sandbox signals only, and a private-volume inode boundary — and it is backed by genuine kernel-effect tests. That is substantially stronger than the hook-only story. It is still not a finished agent isolation boundary, exactly as the README and docs/security/runtime-acceptance.md state: Linux refuses every contained launch, a caged process can still read other same-user processes’ argv+environment (secrets included), killing RV with SIGKILL leaves children holding workspace write authority, descendants never re-enter semantic authorization, and there is no runtime-issued authenticated identity or mandatory audit stream. Several advertised commands (workspace agent, workspace custom, egress approve/deny, workspace abandon) are wired in help but always refuse at runtime.

The hook guard itself (packs, explain, allow-once, scan) is coherent and well-tested. The risk is positioning and UX: present-tense help/README language plus dead-end commands invite users to trust a boundary the code itself — correctly and honestly in its security docs — says is blocked.

2 · Isolation deep dive — what holds, what leaks

2.1 What genuinely holds on macOS today (keep, and say so precisely)

  • Deny-default filesystem fence. compileFirstSliceProfile emits (version 1) (deny default), allows exec/fork, read/map on /usr /bin /sbin /System /Library /dev (the minimum to start programs), read/write only on the canonical workspace subpath, and explicit (deny file-link) (deny file-clone). Outside reads and writes are kernel-denied — verified by SeatbeltContainmentTests, SeatbeltCapabilityTests, and the adversarial suite (traversal, symlink chains, rename-across-boundary, interpolated shells, shebangs, recursive rv).
  • Network: direct egress denied, proxy-mediated HTTPS. No Unix-socket rules at all (a pathless allow would expose every host socket — the comment in SeatbeltProfile.swift is exactly right); outbound TCP only as (remote tcp "localhost:*") to reach the host-side EgressProxy and loopback dev servers. LAN/public/metadata connects return EPERM. The proxy resolves once, requires the whole DNS answer set to be public-unicast, and dials the pinned sockaddr — no check-to-use race, no poisonable pin cache for addresses.
  • Process fence. (allow signal (target same-sandbox)) only; setpgid (82) and setsid (147) denied by syscall number so a descendant cannot leave RV’s process group. posix_spawn deliberately stays allowed (Node/Python/Rust need it) — children inherit the same profile, and the group kill on runtime/workspace close reaps them.
  • Mach/XPC deny-by-default. (deny mach-lookup) (deny mach-register) with exactly one allow (com.apple.bsd.dirhelper, proven necessary for SwiftPM linking; Keychain verified still blocked). This closes securityd/SecurityServer/trustd/pasteboard reachability from the cage.
  • Inode boundary. A pre-existing hardlink inside the workspace refuses launch (workspaceContainsInodeAlias); the workspace path is then mounted on a fresh volume (WorkspaceInodeBoundary) so a later link() to an outside inode fails EXDEV. Publish copies back only when device/inode/kind stamps still match.
  • Descriptor & environment hygiene. POSIX_SPAWN_CLOEXEC_DEFAULT; the child sees only stdio (or the PTY slave), the fd-3 handshake write end (closed by the trusted wrapper before exec), and its own admission pipes on fds 4/5. Ambient fds, loader/interpreter variables, and secret-bearing env are stripped; HOME/TMPDIR point at RV-managed roots. Establishment is proven by an in-sandbox nonce on fd 3 — never by exit code — and a recognized rv-isolation-exec exit 0 is explicitly refused as establishment.
  • Admission narrowness. A contained process may ask RV — over its private pipes, presenting the per-runtime capability — for one shell command (spawned by RV under the same profile, without the pipes) or one HTTPS GET (performed by RV: canonicalized URL, one pinned public address, no cookies/credentials, 64 KiB body cap, 10 s budget, redirects not followed). Replay by request-id or action fingerprint is rejected; runtime A’s pipe cannot act as runtime B.

2.3 Platform split — the Linux story is refusal, and the product copy must own that

Sources/RVIsolation/LandlockRuleset.swift:101 — compileLandlockRuleset validates the plan and workspace, compiles the read+write classes, then unconditionally returns .containedGuaranteesUnsupported (line 148). The C shim handles RV_LANDLOCK_HANDLED_FS beneath the workspace and fail-closes below ABI 3, but system-read layering (/usr, loader), EXECUTE, network, and process guarantees are unenforced, and production launch never reaches it. There has been no supported-kernel (ABI ≥ 3) enforcement run; the audit container kernel (6.10.14-linuxkit) returns ENOSYS. CI now probes the runner ABI and fail-closes when unmeasurable (T8), which is honest — but the README badge (“macOS 15+ arm64 | Linux”) and the platform table (“Linux aarch64/x86_64” as a supported install) read as parity. For the hook guard that is true; for rv opencode / rv workspace a Linux user gets only contained workspace host is unavailable (see UX-03). Either scope the badge/table by feature, or keep Linux contained launch explicitly experimental until a real ABI ≥ 3 run passes the containment suite.

2.4 Egress & credentials — strong design, unfinished production wiring

  • Binary attribution is instance attribution (correctly: TCP loopback carries no peer credentials, and Unix-socket egress would expose every host socket). EgressBinaryPinCache now pins at admission (admit / pinExpected / strict verifyAdmitted), closes the stat/hash window with a post-hash re-stat, and bounds hashing at 256 MiB. The verify-to-use window still needs fd-pinned exec — documented, not hidden.
  • But production does not use it yet. Per the phase-3/4 boundary notes, WorkspaceSessionSupervisor still constructs one shared EgressProxy(record:) per workspace host with no binary scope and no credential. The credentialed mode (EgressProxy(grants:), 256-bit per-principal tokens, 407 denied-credential) and the per-runtime bound instances exist and are tested — the supervisor mint/distribute wiring is the missing step. Until it lands, co-tenant runtimes share one open-mode grant set: rights inheritance by construction. The live supplement (human-approved host:port rules pushed with a generation guard) is likewise honored in open mode only, so one principal’s approved rule is visible to the shared instance.
  • Credential broker is deny-by-default and names-only in audit — the right shape. Two seams remain: legacy .effect transports still drop a granted injection fail-closed as credentialUnwired (only .direct and .effectWithCredential deliver bytes), and AgentHomeStaging.credentialLinks + API-key re-injection are gated behind ContainedCredentialDelivery opt-ins that default closed — good — but the ANTHROPIC_API_KEY=rv-cage-gateway-placeholder public constant stays unconditional, so auditors must compare against the constant, not absence. Pins are in-memory per proxy instance: a restarted proxy re-pins on first use (TOFU window reopens per restart; pinExpected policy digests are the durable answer and should become the recommended configuration).
  • No identity, no audit stream. WorkspaceSessionID/RuntimeSessionID are minted labels; the boundary doc is explicit that knowing an ID is not authentication (the pipe + capability is). What is missing for release is the surrounding record: workspace-sessions.jsonl + runtime-admission.jsonl carry no policy ID, capability set, or kernel-deny events, and launch is not gated on audit success (start-record write does fail closed — the matrix’s §9.5 FAIL is about the absence of a mandatory sink for the tree, not that one line). A user cannot answer “what did this agent do?” from RV’s own logs.

4 · UX review — the guard is honest; the exits are missing

Verified live against .build/debug/rv on this machine (non-TTY probes noted as such). Credit first: rv --help is grouped by task (Get started / Everyday / Advanced) with examples and a Next pointer; rv opencode --help states its isolation limits in plain words including the Linux refusal; the launch banner (OpenCodeRun.isolationNotice) prints the fence summary on stderr before running. That honesty is the product’s best UX asset — the findings below are where behavior diverges from it.

UX-01 P1 — Advertised commands that always fail

Sources/RVCLI/Commands/WorkspaceCommand.swift · EgressCommand.swift · LocalControlBoundary.swift

rv workspace agent <id> and rv workspace custom --expected-content-digest-sha256 … parse, validate (including a 64-hex digest check), then throw operator permits not yet available in runInteractiveSelection before contacting any host. rv egress approve/deny and rv workspace abandon are fully implemented behind LocalControlBoundary.requireOwnerAuthorization(), which unconditionally throws “Authenticated RV service and operation-bound owner authorization required.” — verified live: rv egress approve test123 → that message + generic Usage: rv <subcommand>, exit 64. The user did nothing wrong; the command does not exist yet, but help presents all four as peers of working commands (egress help does add one honest line: “mutations approve and deny refuse until authenticated service routes land” — keep that pattern, extend it).

Fix: mark unshipped commands in help with an explicit (not yet available) suffix and make the runtime error say what is missing and what to do instead (e.g. for egress: “approvals are read-only today; blocked hosts are listed by rv egress pending”). Better: hide agent/custom from help until permits land. Proof: CLI snapshot tests pin help text + refusal wording; a new user can predict the failure from --help alone.

UX-02 P1 — Default output is machine JSON; --plain does not rescue humans

Sources/RVCLI/CommandContext.swift (appearance seam) · live probes

Piped (non-TTY) invocations render robot JSON by design (CI or non-TTY stdout → .robot). Verified: rv test 'git reset --hard', rv explain 'rm -rf ~', and rv doctor each print a single-line JSON object on stdout; adding --plain changed nothing in the piped probes, and rv doctor reported "ok":true alongside "state":"down", "launch_agent":"missing", and "warning":"request failed" — a contradictory health signal. Scripts get a stable contract (good); a human pasting a command into a bug report gets escaped JSON with literal \n sequences inside the explanation string (bad). rv test also exits 1 for a deny verdict, which shell scripts must special-case.

Fix: honor --plain as an explicit human override even when piped (an explicit flag should beat TTY inference); give doctor a graded verdict (degraded ≠ ok) in both formats; document the test exit-code contract in its help. Proof: golden-output tests for --plain piped vs. TTY; doctor fixture with service down asserts non-ok.

UX-03 P1 — Linux refusal gives no next step, and wording differs by entry point

OpenCodeCommand.swift:87 · WorkspaceCommand.swift (8× “contained workspace host is unavailable”)

On Linux every contained command throws the bare ValidationError("contained workspace host is unavailable"). It does not say the hook guard still works, that only the contained runtime is macOS-only, or where to read why. The opencode help text does say it well (“Linux refuses launch until it can enforce the same limits”) — the runtime error should match its own help.

Fix: one shared refusal string: “contained runtimes are macOS-only today — the Linux sandbox cannot yet enforce the same limits, so rv refuses rather than run unsandboxed. Hook protection (rv setup / test / explain) works on Linux. See docs/security/runtime-boundary.md.” Proof: Linux CI smoke asserts the string; macOS unaffected.

UX-04 P2 — Accepted risks (R1/R2/R3) are documented in security docs but invisible at launch

OpenCodeRun.isolationNotice · HelpCatalog (opencode “limits” row)

The launch banner says “loopback networking is allowed” / “loopback allowed”. It does not say a caged server can be reached from the LAN (R1), from other workspaces or host processes (R2), or that same-user temp files are readable (R3). A user running a dev server with test data in the cage reasonably believes “loopback” means “only this machine, only me.” R1 means the first half is false.

Fix: add one banner line: “Note: servers the agent starts on loopback can also be reached from your LAN and by other local processes — treat caged ports as LAN-visible.” Mirror it in the help “limits” row. Proof: help/banner snapshot tests.

UX-05 P2 — Workspace lifecycle errors are terse at exactly the scary moments

WorkspaceCommand.swift:190–301 · WorkspaceRecovery / WorkspaceInodeBoundary errors

workspace host is not reachable, stale endpoint, abandon failed, and the WorkspaceHosts.inspect text dumps tell the user what but never what to do: is the volume still mounted? Are unpublished changes safe? Should they run workspace abandon (which itself refuses per UX-01), rv doctor, or reboot? A blocked workspace holding the only copy of agent work is the highest-anxiety state in the product, and its recovery path currently dead-ends at the owner-authorization gate.

Fix: every lifecycle refusal gains a state + next action pair (e.g. “workspace volume is still mounted at <path>; your unpublished changes are intact. Run rv workspace status, then rv doctor. If the host died, rv workspace abandon restores the saved tree.”), and ship the abandon path (or a documented manual recovery) before promoting persistent workspaces. Proof: kill-the-host integration test walks status → recovery unattended.

UX-06 P2 — rv opencode without --resource-profile fails late, inside the cage

OpenCodeCommand.swift — missingProfileWarning

The warning is honest (“provider credentials are unstaged and agent auth will fail”) but non-blocking by design so keyless runs (local models, --help) keep working. The failure then surfaces as the agent’s own provider auth error inside a sandbox the user may not realize strips credentials — support tickets will blame the provider. workspace run has the same shape with less warning.

Fix: keep the non-blocking default, but name the remedy in the warning (--resource-profile <id>; list available IDs via the profiles command) and mirror it on workspace run. Proof: first-run walkthrough test with no profile → warning visible before spawn in captured stderr.

UX-07 P3 — Small frictions

  • Bare rv means “open the workspace shell” while the abstract says “Block destructive shell commands” — in a non-TTY it errors “workspace shell requires an interactive terminal” (correct, but the mapping surprises). Consider printing help when stdin/stdout are not TTYs instead of an error.
  • rv workspace --help renders agent/custom rows with long inline descriptions that break the column layout (observed overflow in terminal output). Move detail to per-subcommand help.
  • Validation errors are single-sentence ValidationErrors with no error codes; egress uses structured ctx.fail(…, exitCode: 2) — converge on the egress pattern (stable prefix + exit code) so failures are scriptable and searchable.
  • The Workspace TUI signals runtime state by color alone (WorkspaceTUIApp: ● red/yellow/green; pane borders green/gray). Add a text label beside each indicator for color-blind users and screen-reader transcripts.
  • Shell completions were modified in the working tree for the new commands — verify Resources/Completions/* cover egress subcommands and do not complete the not-yet-available paths as if functional.

5 · Bugs & implementation gaps (beyond the Isolation holes)

BUG-01 P2 — rv doctor reports ok:true while its own payload says the service is down

Sources/RVCLI/Commands/DoctorCommand.swift · live probe

Observed: {"ok":true, "service":{"state":"down","launch_agent":"missing","warning":"request failed"}, "grade":"hook"}. Whatever grade:"hook" means internally, a top-level ok that coexists with a down service and a missing LaunchAgent will be read — by humans and by scripts gating on .ok — as healthy. Fix: derive ok from the worst component, or replace it with a graded status: ok|degraded|down. Proof: fixture with service down asserts not-ok.

BUG-02 P2 — Explain’s human explanation is stored with literal escape sequences
