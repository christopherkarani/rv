Who gets to say no

Coding agents run our shells now. The checkpoints we built check the wrong moment.

Chris Karani · Aug 2026 · DRAFT v5

In July 2026 an agent on a Windows machine was asked to clear an app's tmp cache. The command it ran contained a shell variable in quotes. The outer shell expanded the variable to nothing, so what the safety layer approved and what rm actually executed were two different commands. One was harmless. The other spent four minutes deleting /bin, /boot, /etc, and everything the user owned.

When the user tried to kill the process, the agent's own safety layer blocked it. Killing the agent counted as interfering with its work. Deleting his files didn't.

That's issue 82165 against Claude Code. It's not even the worst one. There's a developer who watched a quoting mistake turn an approved file copy into `rm -rf /*` on a production server. Two companies' sites gone, plus their databases and SSL certificates. There's a guy whose home directory vanished because the agent created a folder literally named `~` and then deleted it. There's a typo — one transposed letter in a path — that macOS's case-insensitive filesystem quietly resolved to the real project folder, uncommitted work and all.

Every one of these went through some kind of checkpoint first.

I've been thinking about why, because I write code with these agents every day and I'm not going to stop. And I think the answer is that we built the checkpoints for the command we read, when the danger lives in the command the shell hears. Everything else follows from that mistake.

Consider the main defense: ask the human. Anthropic published the numbers themselves. Users approve 93% of permission prompts. At that point the prompt isn't oversight. It's a rubber stamp with extra keystrokes. The people who study warning dialogs for a living figured this out years ago; click-through rates of 33 to 70 percent show up in every serious study, and one economist pointed out something uncomfortable, which is that ignoring warnings is rational. When they almost never matter, you should stop reading them.

Why not make the dialog smarter? So vendors tried: let a model judge whether a command looks dangerous. Anthropic measured this too. Their classifier misses about 17% of genuinely overeager actions. But here's the detail worth sitting with. The misses aren't random. The classifier reads the same text the human did. A double-quoted SSH string. A variable inside quotes. A case-insensitive filesystem. The shell outsmarts the pattern, and destruction happens after the checkpoint has already said yes.

The problem isn't stupidity. It's timing.

All these defenses check the command before expansion, and the shell rewrites it after. It's like inspecting passengers at the airport door and letting anyone who makes it past swap briefcases at the gate. You checked the right thing at the wrong moment.

This is why I wrote rv. It's a small Mac tool that hooks into your coding agent's shell and evaluates commands after they're expanded, right before execution. Recursive deletes outside temp dirs get denied. Force-pushes get denied. The rule set is deliberately small, and each denial comes with a note saying which rule fired and why.

You might say: just use a sandbox. Sandboxes are great. Docker's microVMs, devcontainers, E2B, they're the best blast-radius reduction available and I recommend them. But notice which question they answer. They protect the host from the workspace. Most of us have a different problem: we want the agent working on this Mac, in this repo, with these credentials, because that's where the work is. Run your agent in a container with your project bind-mounted and `rm -rf` deletes your real files just as dead. If the workspace is the thing you're protecting, the guard has to sit where the command runs.

Designing rv meant deciding what it does when it's unsure. That turned out to be the whole design.

If rv can't parse the payload a hook sent it, it blocks. That sounds harsh until you see the alternative. A deny-list fails by allowing, silently; you never find out. An allow-list fails by refusing, loudly, and someone fixes it. Saltzer and Schroeder wrote this down in 1975 and it hasn't aged a day. Unknown commands are allowed, though, and that's deliberate. rv ships with few rules precisely because a guard that blocks everything it doesn't recognize gets disabled within the hour, and a disabled guard is worse than none.

But there's an escape hatch. On Grok, if rv stops something you actually meant to run, you can mint a one-time unlock scoped to that exact command in that exact folder, and next time it asks again. Not on Pi or OpenCode yet. Their hook payloads don't carry the working directory, and I won't scope an unlock to less than command-plus-folder, because "trust this command anywhere" is how you end up back where you started.

What about trust? Two honest disclosures, because you'd find them eventually anyway. Anonymous install counts leave your machine via PostHog. No command text or paths ever; evaluation happens entirely on your Mac. And rv works at the hook layer. It is not a sandbox. A process that skips the hook entirely never meets rv. I could have blurred that and nobody would have noticed for months, but you'd find out at the worst possible time, so: hook-grade, that's all it claims to be.
